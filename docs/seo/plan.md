# SEO・AEO 第1段階: 公開構造の調査と、教材 URL・本文 HTML の配信設計(Issue #13、親 Issue #12)

調査と設計の文書。この PR では、アプリのコード、教材、出典、確認日を変更していない。ドメインの購入、DNS、Search Console の登録、本番公開の設定変更も、していない。Codex と Claude の確認は、専門家の監修でも、利用者の検証でもない。**検索順位や AI での引用は、保証しない。** 現在の検索順位、被リンク、Search Console の状況、実測の表示速度は、**未確認**(初期値がないので、増加率やアクセス数の目標も書かない)。

## 0. 要約

- **現状**: 公開サイトは、HTTP で取得できる HTML に本文がない(`<div id="root">` だけで、`<title>` は全ページ共通)。URL はハッシュ(`#/lesson/pm-1`)で、サーバーには送られない。どの教材も、検索エンジンから見ると、同じ 1 つの URL に見える。ページ別の説明、canonical、サイトマップ、共有情報、構造化データ、計測は、ない。存在しない URL は、アプリの中で別のページに飛ばされ、HTTP 200 を返す(soft 404 の形)。
- **推奨案(1 つ)**: **現行の React / Vite を活かし、ビルド時に、全ページの HTML を書き出す**(自前の薄い事前生成。フレームワークの移行はしない)。URL は、パスの形(`/lesson/pm-1/`)にする。ブラウザでは、同じコンポーネントが、その HTML を引き継ぐ(ハイドレーション)。教材の本文は、今のとおり、Markdown と TSX の 1 か所だけで書く。
- **根拠(今回の実験)**: 引き継ぎ用の出力(`renderToString`)で、172 レッスンすべての本文を、Node で HTML に描画できた(1.0 秒、合計 1.4 MB)。**現行のビルド(索引用)が使う `renderToStaticMarkup` は、出力を引き継げないので、同じ方法ではない**(§2.7 E1)。ブラウザでの引き継ぎ(`hydrateRoot`)は、172 件中 165 件が警告なし、7 件に不一致があり、**7 件とも原因を確認した**(数値の最後の桁 3 件は、差分の中身で。並べ替え問題のランダムな初期順 4 件は、決まった初期順にした一時的なコピーで、不一致が 0 件になることで)。アプリの枠ごとの引き継ぎは、`useProgress` に、**安定した**初期値を返す `getServerSnapshot` を足せば、講座一覧・講座の目次・地図・ロードマップ・用語集・出典の一覧の 6 ページで、保存済みの進捗がある状態でも、ない状態でも、不一致 0 件で、進捗が上書きされないことを確認した(§2.7 E5)。**レッスンページの枠は、本文を事前に渡す変更が要り、未検証**。
- **決めること**(§7): PM(Codex)が、技術的な提案として引き受けた事項(通常 URL の形、noindex の対象、og:image を第1段階で省くこと、旧リンクの救済を残す期間、進捗の書き出しの限界の扱い)と、**作者に残る判断**(ドメイン名、継続費用、公開範囲と利用条件、実際の移行・公開のタイミング)を分けた。
- **追加の設計条件(Issue #13 の追加コメント。§8〜§12)**: 将来の小さな収益化、公開範囲(リポジトリの private 化)、GitHub Free を踏まえ、配信先を比較した。**当面は、現状(公開リポジトリ + GitHub Pages)のまま、設計を配信先に依存しない形にする**。GitHub Pages の条件は、主に商取引を促進する、または商用 SaaS のサイトを許可しておらず、公開リポジトリを private にすると、Free では Pages が停止する。private 化の前に、新しい配信先での公開確認、旧 URL・出典リンク・進捗の案内、切り戻しを整える順序を提案した(§10.4)。収益化の前に別途確認する、ライセンスの範囲(NC 資料を含む 21 教材など)も、記録した(§10.3)。**可視性の変更、プラン変更、契約、移行、ライセンス変更は、していない**。未解決の点は §12。 **追加のレビュー(7d55823)を受けて**: 本番は、当面そのまま維持し、少数ページの試作は、別の検証環境で行い、全展開・移行は、配信先の調査とレビューの後に決める(§9.3)。private 化では、旧 Pages の案内・転送・進捗の書き出しの画面も停止するので、**新サイトの停止を防ぐ順序と、旧サイトの救済を保つ順序を、別に設計**した(§10.4a)。GitHub を指すリンクは、**誤りの報告先を含む 4 種類**(§10.5)。収益化の方向は、無料教材で認知と信頼を作り、独自の実践キットを、買い切りで小さく試す(価格・目標額・販売開始日は、未定)。

### 2.6 進捗の書き出し・読み込み(ドメイン移行の救済に使えるか)

保存の仕組み(コード): 進捗は、`localStorage` の `llm-learning:progress` に、1 つの JSON で保存される(`src/progress.ts`)。自己診断の回答は、別のキー `llm-learning:assessment`(進捗率や書き出しには含めない設計)。API の設定は `llm-learning:api-settings`、API キーは `sessionStorage` の `llm-learning:api-key`(書き出しに含めない設計)。進捗画面に、書き出し(JSON のダウンロード)と、読み込み(JSON のファイル)がある。

実験(Playwright。テスト用のまっさらなプロファイルに、テスト用のデータを置いた。ユーザーのデータは、読んでも、変えてもいない):

| 項目 | 結果 |
|---|---|
| 書き出された内容 | `version`、`completed`(読了)、`quiz`(クイズの最高点)、`questions`(問題ごとの正誤の記録=復習の対象)、`reading`(読み位置)、`lastVisited` |
| 書き出されない内容 | 自己診断の回答(`llm-learning:assessment`)、API の設定、API キー(テストで、ファイルにキー文字列がないことを確認) |
| 別のプロファイルで、画面の「インポート」から読み込む | 進捗が完全に一致した(読了、クイズ、復習の記録、読み位置、最終訪問のすべて)。画面の案内は「進捗を読み込みました。」 |

- 限界: 自己診断の回答は、引き継げない(設計どおり)。**移行で救済できるのは、読了・クイズ・復習・読み位置・最終訪問**。
- `localStorage` は、**オリジン(スキーム+ホスト+ポート)ごと**に分かれる(ウェブの標準の仕組み。今回は実験していない)。パスの形への切り替えは、同じオリジン(`https://shn4pt.github.io`)の中なので、保存データは、そのまま使える(推定。試作で確認する)。**ドメインを変えると、オリジンが変わり、保存データは見えなくなる**。そのとき、書き出し・読み込みが、救済になる。
- 同じオリジン(`shn4pt.github.io`)に、将来、別のプロジェクトのサイトを置く場合、`localStorage` が共有される。キーは `llm-learning:` で始まるので、衝突は、まず起きないが、独自ドメインに移ると、この共有もなくなる。

### 3.3 推奨: A(現行の React / Vite を活かして、ビルド時に全ページの HTML を書き出す)

理由:
1. 教材は静的で、事前に HTML にできる。実際、**引き継ぎ用の出力(`renderToString`)で、172 レッスンすべての本文を、1.0 秒で HTML に描画できる**(E1。現行のビルドの索引用の描画は `renderToStaticMarkup` で、その出力は引き継げないので、本番の生成は、`renderToString` と `hydrateRoot` を使う)。必要なのは、描画結果を、ページごとのファイルに書き出す工程と、ブラウザでの引き継ぎだけ。
2. 変更が、最小限で済む(§5.3 の主要ファイル)。フレームワークの人気を理由に、移行を選ばない。
3. 静的ファイルなので、配信先に依存しない(現在の GitHub Pages でも、独自ドメインでも、将来、別の静的ホスティングでも、同じ成果物を載せられる。§9)。サーバーの運用が要らない。
4. 本文を二重に書かない(同じ Markdown / TSX から、HTML とアプリの両方が作られる)。

残るリスク: ①ハイドレーションの不一致(E2 の 7 件は、原因を確認済み。E5 で、レッスン以外の 6 ページの枠は、進捗のある状態でも、不一致 0 件。**レッスンページの枠(本文の事前の受け渡し、クイズ、しおり、完了ボタン)は、未検証**)。②GitHub Pages の `404.html` が、404 のステータスで配られるか(試作で確認)。③ビルドと CI の時間の増加(未測定)。④将来、ページ数が大きく増えたときの、生成時間(現状 172 レッスンで 1.0 秒なので、当面は問題にならない見込み)。

B に移る理由が、あとから出てくる条件(例): 事前生成スクリプトの保守が、想定より重くなった場合、画像最適化や多言語など、フレームワークの標準の機能が必要になった場合。そのときは、A の成果(パスの URL、メタ情報のデータ、サイトマップ)を引き継げる。

### 4.2 HTML に含めるものと、JS で動かすものの境界

| 内容 | HTML(JS なしで読める) | JS で動く(ハイドレーション後) |
|---|---|---|
| ヘッダー、パンくず、題名、概要、所要時間の目安 | ○ | リンクの遷移(History API) |
| 教材の本文(Markdown / TSX の本文) | ○(E1 のとおり、同じコンポーネントから生成) | |
| 判定問題・実験ツールなどの対話部品 | 初期の状態の HTML(問題文、選択肢、操作部品の見た目)は出る | 答え合わせ、スライダー、実験の操作 |
| クイズ | 問題文と選択肢は出る(未回答の状態)。解説は、回答後に出る(HTML には、ない) | 回答、採点、復習への記録 |
| 出典と更新記録(`SourceNote`)、利用条件の表示 | ○(折りたたみの中身も HTML にある) | 折りたたみの開閉 |
| 前後のレッスンへのリンク | ○(`<a href>`) | |
| 進捗、完了ボタンの状態、しおり、続きから読む | 初期状態(未完了)で出る | 保存データを読んで、更新(`getServerSnapshot` は空の状態を返す) |
| Claude API を使うデモ | 画面の枠と説明 | キーがある場合の呼び出し(キーがなくても、読めて、操作の前までが動く状態を保つ) |

- **進捗と個人のデータ**: 生成 HTML には、個人の進捗を含めない(初期の状態=空)。`useProgress` の `getServerSnapshot` は、**モジュールの定数**(安定した初期のスナップショット。React は、繰り返しの呼び出しで、同じ値を要求する。§2.8)を返す。ブラウザは、ハイドレーションの後に、保存済みの進捗へ更新する。**ブラウザの保存データを、初期値で上書きしない**(E5 で、進捗の JSON が、同じままだった)。生成の側は、`localStorage` を読まない(Node に `localStorage` はなく、`load()` は、読めないとき、空で始まる)。
- **生成の方法**: 本番は、`renderToString` と `hydrateRoot` を使う(`renderToStaticMarkup` は、出力を引き継げないので、使わない)。サーバーとブラウザは、**同じコンポーネントの木**を描画する。サーバーからブラウザへ渡す初期値は、①ルート(パス)、②レッスンの本文(事前に読み込んだ内容。同じモジュールから)で、**進捗は渡さない**(空の初期値で描画し、ブラウザで更新する)。乱数・時刻・ロケールに依存する値は、初期の描画に使わない(E2 で見つかった、`CodeOrder` の最初のランダムな並びと、数値の丸めの 2 種類を直す)。

- 同じ本文を二重に管理しない: HTML は、アプリと同じコンポーネントを、ビルド時に描画して作る。別のテンプレートに、本文を書き写さない。
- **JS が必要な機能の、読者への表示**: レッスンの対話部品の近くに、JS が必要なことを示す(`<noscript>` の案内。最小限)。この文言は、試作で決める。

### 4.3 直接アクセス・再読み込み・存在しない URL

- 直接アクセス・再読み込み: 該当のページの HTML が返る(200)。ブラウザは、HTML を引き継ぐ(ハイドレーション)。
- 存在しない URL: GitHub Pages が `404.html` を、404 のステータスで返すように、`404.html` を置く(アプリの殻。`noindex`)。アプリは、未知のルートを、別のページに移動せず、「見つかりません」の表示にする(現行の「ロードマップ」や「講座一覧」への移動は、やめる)。存在しないレッスン ID も、同じ。これで、soft 404 を避ける。**`404.html` が、本当に 404 のステータスで配られるかは、未検証で、試作の受け入れ条件にする**。
- 存在しないレッスン ID・講座 ID・ステージ ID(パスの URL でも、旧ハッシュ形式でも)は、**同じ扱い**にする: 「見つかりません」の表示と、講座一覧へのリンク。旧形式の未知の ID を、講座一覧へ移さない(移すと、存在しない URL が、別のページとして見えてしまう。PM の推奨)。
- アセットの解決: ベースのパスを絶対にするので、深いパスでも、アセットが解決できる。
- 重複ページ: `/` と `/catalog/` は、同じ内容の HTML で、canonical は **`/catalog/` に統一する**。`/index.html` と `/` は、GitHub Pages では同じ URL として配られる(標準の動作。試作で確認する)ので、別のページとして扱わない。ハッシュ付きの旧 URL は、HTTP では `/` と同じ(§4.6)。

### 4.4 ページ別のメタ情報、サイトマップ、検索向けに公開するページ

- **ページ別の title / description / canonical / 共有情報**: 新しいデータは、書かない。既存のデータから、生成する。レッスン: タイトルは、`curriculum.ts` のレッスンの題名と、サイト名(「PM-1 PM の仕事の全体像 | 独習アカデミア」の形)、description は、レッスンの `summary`。講座: `catalog.ts` の講座名と、入口データ(`course-entry.ts`)の「どんな判断に役立つか」。講座一覧、地図なども、同様。canonical と OG の `og:url` は、`SITE_ORIGIN` と `SITE_BASE` から。`og:title`、`og:description` は、title と description と同じ。`og:image` は、画像がないので、第1段階では付けない(画像の用意は、別の判断)。
- **サイトマップ**: ビルド時に、`curriculum.ts` と `catalog.ts` から生成する(§2.4 の対象、196 件)。`<lastmod>` は、`lesson-history.json` の最終コミット日があれば使い、なければ省く(見込みの日付を、書かない)。置き場所は、`<ベース>/sitemap.xml`(Google の資料のとおり、置いたディレクトリの下の URL に効く)。
- **robots.txt**: ホストの直下にしか置けないので、**独自ドメインの決定後**に、`sitemap.xml` の場所の記載とあわせて、置く。いまは、置かない(GitHub Pages のプロジェクト配下では、効かない)。
- **検索向けに公開しないページ**: 進捗、復習、検索、API キーの設定、404 のページは、`<meta name="robots" content="noindex">`(静的ホストでは、HTTP ヘッダを付けられないので、メタタグ)。これらは、ユーザーごとの状態を扱い、検索で見つかる価値がない。内部検索の結果ページは、公開の URL に載せない(検索の索引は、サイト内の機能)。

### 4.4a ブラウザ内のページ移動での、メタ情報と noindex の更新

- 初期 HTML の生成と、ブラウザの中のページ移動(History API。HTML の全体を取得し直さない)で、**同じルート別メタ情報の関数**(§5.2 の `src/seo.ts`)を使う。移動のたびに、`<title>`、`description`、canonical、OG、`robots` を、現在のルートへ更新し、不要になったタグ(例: `noindex`)は、**除去**する。履歴の戻る・進む(`popstate`)でも、同じ関数で整合させる。タグを重複させない(既存のタグを探して書き換え、なければ作る)。
- 理由: 最初に開いたページのメタ情報が残ると、①`/progress/` の `noindex` が、公開教材へ移動した後も残る、②PM-1 の canonical が、別の教材でも残る、といった問題が起きる。Google の資料は、title・description・canonical を、JS で設定できるとしている(canonical を、別の URL に変えない。§2.8)。ただし、**各 URL の初期 HTML が、その URL のメタ情報を、正しく持つ**ことを、基本にする(JS による更新は、ブラウザの表示、履歴、共有のため)。
- 実装の形(案): ルート変更を購読する小さなコンポーネント(または、ルーターの `useEffect`)で、`applyMeta(routeMeta(pathname))` を呼ぶ。関数は、既存のデータから作る(§4.4)。

### 4.5 CSP と構造化データ

- CSP は、**現行のまま維持する**(`script-src 'self'`、`connect-src` は自サイトと Claude API)。検索対応のために、API キーの保護を弱めない。メタタグの CSP も、生成する全ページに付ける(今は `index.html` だけ。ビルドの変換で付く)。
- **構造化データ**: 第1段階では、**入れない**(Claude の設計判断)。Google は、AI 機能への表示に、特別な構造化データを要求しない。必要になれば、E4 のとおり、JSON-LD は CSP の下でも置ける(データのブロック)。入れるなら、表示される内容と合うものに限る(例: 講座の名前と説明。本文と合わない主張を入れない)。
- 旧リンクの転送などの、実行する JS は、**インラインにせず、外部ファイル**(`<ベース>/assets/` のスクリプト)にする(E4)。

### 4.6 旧リンク(`#/lesson/pm-1` など)の救済

- フラグメントは、サーバーに送られない(MDN)ので、**サーバーの転送だけでは、教材ごとの移転は完了しない**。旧リンクは、HTTP では `/dokushu-academia/`(ルートの HTML)を取得する。
- 提案: ルートの `index.html`(と、全ページの殻)に、小さな外部スクリプトを読み込み、**`location.hash` が `#/` で始まる場合だけ**、パスの URL(`<ベース>/<path>/`)へ `location.replace` で移す。たとえば `#/lesson/pm-1` → `/dokushu-academia/lesson/pm-1/`。存在しない ID は、移さず、パスの URL の「見つかりません」の表示と、講座一覧へのリンクにする(旧形式でも、講座一覧へは移さない。§4.3)。JS が実行されない環境では、ルートの HTML(講座一覧と同じ内容)が見える。
- 限界: 旧ハッシュ URL を、検索エンジンが、教材ごとの別 URL として登録しているとは想定しない(Google は、フラグメントをサポートしない)。外部に出回った旧リンクが、JS を実行するブラウザで、新 URL に移る、という救済で、検索の評価の引き継ぎは、期待しない。
- この転送を残す期間: **期間で切らない**。少なくとも、**新しい配信・ドメインへの移行後の確認まで**は残す(PM の提案を採用)。終了を判断するときに、改めて検討する。外部に出回った旧リンクの数は、未確認。

### 4.7 ドメイン変更時の `localStorage`、書き出し・読み込み、切り戻し

- **パスの URL への切り替え**(同じ `https://shn4pt.github.io` の中): 保存データは、そのまま使える見込み(オリジンが同じ。試作で確認する)。
- **独自ドメインへの移行**: オリジンが変わり、保存データは見えなくなる。救済は、既存の「エクスポート」→新ドメインで「インポート」(§2.6 の実験で、読了・クイズ・復習・読み位置・最終訪問が復元できることを確認済み)。
  - 案: 旧ドメイン側の進捗画面(と、講座一覧の上部)に、移行の案内と、エクスポートへの導線を、一定期間表示する。案内の文面は、独自ドメインが決まってから書く。
  - 限界: 自己診断の回答は、書き出しに含まれない(設計)。含めるかは、作者の判断(§7)。API の設定と API キーは、含めない(設計どおり。再入力が要る)。
- **切り戻し**: 事前生成とパスの URL は、リポジトリの `main` に入れるので、問題があれば、`git revert` で、前のビルド(ハッシュの URL)に戻せる。独自ドメインへの移行は、DNS の変更で、元の `github.io` の URL に戻せる(GitHub の手順に従う。設定の詳細は、ドメイン決定の段階の調査で扱う)。

### 4.8 ドメインが未定でも進められる試作の範囲と、決定後に変える設定

- 進められる: パスの URL、ビルド時の事前生成、ハイドレーション、ページ別メタ情報、サイトマップ、404、旧ハッシュの転送、`noindex`。ドメイン未定の間は、`SITE_BASE=/dokushu-academia/`、`SITE_ORIGIN=https://shn4pt.github.io` で動かす。
- 決定後に、設定だけで変える: `SITE_BASE`(`/`)、`SITE_ORIGIN`(新ドメイン)、`CNAME`、robots.txt(ホスト直下)の追加、canonical とサイトマップの再生成、Search Console の登録、旧ドメインからの案内。

- **URL の空間を分ける**: 公開教材は、`/lesson/`、`/course/` など(§4.1)。有料機能や購入者向けのページは、別のオリジン(別のサブドメイン、または別のサービス)に置く案を、基本とする。同じオリジンに置くと、`localStorage` と CSP が共有され、現行の CSP(`connect-src` は、自サイトと Claude API のみ。API キーを守る前提)の見直しが要る。**別のオリジンにすれば、公開教材の CSP と、保存データを、そのまま保てる**。最終的な構成は、収益モデルの決定後に決める。 ただし、進捗の同期など、**公開教材側から API を使う場合は、CSP(`connect-src`)の変更が、要る可能性がある**。**別のオリジンにすれば、CSP の変更が不要になる、とは保証しない**。最終的な通信経路は、その機能を設計するときに、確認する。
- **決済は、外部のサービスにリンクする形**を、最初の候補にする(今は、選定しない)。ただし、**GitHub Pages に、外部決済へのリンクを置くことが、Pages の条件に合うかは、一律には言えない**(§9.1。「主に商取引を促進するサイトか」の判断で、サイト全体の目的による。GitHub への確認が要る)。
- **進捗の同期**(将来の、任意の機能): 公開教材の読み方には、アカウントを要求しない。同期を足すなら、**現行のエクスポート形式(`version: 1` の JSON)を土台**にして、データの形式の互換を、`version` で管理する(§2.6)。個人データの扱いは、導入時に、別途、確認する(法務)。API キー・学習者の回答・進捗の本文を、検索のメタ情報や分析に送らない(Issue #12 の制約)。
- **計測**: 認知拡大の段階では、必要最小限(別の段階で設計)。購入者機能は、公開教材の計測と、分ける。

### 10.4a private 化の後も、旧 URL・進捗の救済を続けられるか

**新サイトの停止を防ぐ順序(§10.4)と、旧サイトの救済を保つ順序は、別に設計する。**

- **事実**: GitHub Free で、現行のリポジトリを private にすると、**旧 Pages(`https://shn4pt.github.io/dokushu-academia/`)は、自動で公開停止になる**(公式。§9.1)。そこに載せた、新 URL への案内・転送・進捗の書き出しの画面も、同時に停止する。**現行のリポジトリを private にするだけでは、旧 Pages の救済は、維持されない**。新サイトが動くことの確認(§10.4 の手順 4)は、旧リンクを開く人や、移行を知らず、旧オリジンに進捗を残している人の救済を、保証しない。
- **旧オリジンの性質**: 進捗は、オリジン `https://shn4pt.github.io` の `localStorage` にある。`localStorage` は、パスではなくオリジン単位なので(ウェブの標準の仕組み。今回は、実験していない)、**このオリジンの、どのページからでも、読み書きできる**。旧 Pages が停止しても、**同じオリジンで、別の公開ページを残せば、進捗の書き出しと、案内を、続けられる可能性がある**(**未検証**)。
- **候補**(**具体的な方法を検証せず、確定しない**。履歴の削除・書き換えは、依頼されておらず、どの案でも、前提にしない):
  1. **移行専用の、公開の成果物を残す**: 移行の案内、旧 URL から新 URL への転送(JS)、進捗の書き出しだけを含む、小さな公開サイトを、旧オリジンに残す(別の公開リポジトリ。例: ユーザーサイト用の `shn4pt.github.io`、または、公開のままの旧リポジトリとは別のもの)。開発用の private リポジトリとは、分ける。**この成果物が、旧 URL(`/dokushu-academia/…`)への要求を、受けられるか**(旧 URL のパスは、リポジトリ名と同じ。ユーザーサイトの 404 ページが、別のリポジトリのパスへの要求を受けるか。リポジトリ名の変更・移転の影響)は、**未確認**。GitHub Pages の条件(商取引を主目的にしない)は、この成果物にも、適用される(案内だけのサイトにする)。
  2. **開発用の private リポジトリと、旧公開サイトを、別のリポジトリにする**: 現行のリポジトリは、private にせず、旧サイト・移行の案内用として、公開のまま残し、今後の開発を、新しい private リポジトリへ移す。公開リポジトリに、既存の公開物が残る(回収にならない。§10.3)。
  3. **旧側を残さない**: 案内の期間を設け、終了時の影響(旧リンクが開けない。旧オリジンの進捗を、書き出せなくなる)を、読者に提示し、**作者が受け入れてから**、実施する。
- **維持するもの・終了するもの(案。決めるのは、作者)**:

| 項目 | 候補 1・2 | 候補 3 |
|---|---|---|
| 旧 URL からの転送と、新 URL の案内 | 維持できる可能性(転送は JS で、サーバー側の 301 ではない。未検証) | 案内の期間の後に、終了 |
| 進捗の書き出しの画面(旧オリジン) | 維持できる可能性(未検証) | 終了。終了後は、旧オリジンの進捗を、書き出せない(ブラウザの保存データは残るが、読む手段がない) |

| 旧 URL の、検索結果への露出 | 評価の引き継ぎは、保証しない | 同じ |

### 10.5 出典・ライセンスのリンクを、private 化しても、読者が確認できるようにする

現状、アプリが、GitHub のリポジトリを指すリンクが、**4 種類**ある(`src/sources.ts` の `REPO`)。

| 場所 | リンク先 | private 化したときの影響 |
|---|---|---|
| 全ページのフッター(`src/App.tsx`) | `<REPO>/blob/main/LICENSE-CONTENT.md`(ライセンスの詳細) | 読者には、見えなくなる(404) |
| レッスン末尾の利用条件の表示(`src/ui/SourceNote.tsx`) | `<REPO>/blob/main/docs/licenses.md`(扱いの方針) | 同上 |
| レッスン末尾の更新記録(同) | `<REPO>/commit/<ハッシュ>`(コミット) | 同上 |
| 出典の一覧ページの「誤りを見つけたら、リポジトリでお知らせください」(`src/pages/SourcesPage.tsx:26`) | `<REPO>/issues`(**誤りの報告先**) | 一般の読者は、ここへ報告できなくなる |

- `LICENSE-CONTENT.md` 自身は、公開サイトの URL を、表示の例として載せている(サイト側)。CC のライセンスへのリンクは、`creativecommons.org` で、リポジトリに依存しない。
- 提案(設計のみ。実装しない): **ライセンスの文書を、公開サイトの静的なページ(例 `/license/`)として公開する**。同じ Markdown(`LICENSE-CONTENT.md`、`docs/licenses.md`)から、ビルド時に生成し、**二重に管理しない**(§4.2 の考え方と同じ)。フッターと利用条件の表示のリンクを、そのページに向ける。**更新記録**は、すでにサイトが持つデータ(`lesson-history.json`: 日付、ハッシュ、題名)を、そのまま表示でき、**コミットへのリンクは、リポジトリが公開の間だけ有効**にする(private 化の前に、外す)。これで、private 化しても、読者が、出典・ライセンス・更新の記録を、確認できる。**出典の記録(`lesson-sources.json`)は、サイト内に表示されており、リポジトリに依存しない**。
- **誤りの報告先**(4 種類目): private 化すると、一般の読者は、`<REPO>/issues` へ、誤りを報告できない。移行のチェックに加え、**公開の連絡先・報告用の場所へ向ける**か、**代替が決まるまで、この案内の文言を変える**(例: 報告の受付を、一時的に案内しない)設計にする。**現在の private な開発用 Issue を、一般の読者に開く必要は、ない**。問い合わせ用のアカウントや、外部サービスの作成は、今回は、行わない(次の段階で、作者が決める)。
- 位置づけ(PM の方針): ライセンス文書の公開ページ化は、**本番の private 化の前の必須作業**。試作に含めるかは、次の Issue で PM が範囲を決める(作者に、この小さな実装範囲の判断を、求めない)。

- このリンクの付け替え(**4 種類。誤りの報告先を含む**)は、**private 化を判断する前に、完了している**ことを、§10.4 の手順 4 の確認項目にする。
