# SEO・AEO 第1段階: 公開構造の調査と、教材 URL・本文 HTML の配信設計(Issue #13、親 Issue #12)

調査と設計の文書。この PR では、アプリのコード、教材、出典、確認日を変更していない。ドメインの購入、DNS、Search Console の登録、本番公開の設定変更も、していない。Codex と Claude の確認は、専門家の監修でも、利用者の検証でもない。**検索順位や AI での引用は、保証しない。** 現在の検索順位、被リンク、Search Console の状況、実測の表示速度は、**未確認**(初期値がないので、増加率やアクセス数の目標も書かない)。

## 0. 要約

- **現状**: 公開サイトは、HTTP で取得できる HTML に本文がない(`<div id="root">` だけで、`<title>` は全ページ共通)。URL はハッシュ(`#/lesson/pm-1`)で、サーバーには送られない。どの教材も、検索エンジンから見ると、同じ 1 つの URL に見える。ページ別の説明、canonical、サイトマップ、共有情報、構造化データ、計測は、ない。存在しない URL は、アプリの中で別のページに飛ばされ、HTTP 200 を返す(soft 404 の形)。
- **推奨案(1 つ)**: **現行の React / Vite を活かし、ビルド時に、全ページの HTML を書き出す**(自前の薄い事前生成。フレームワークの移行はしない)。URL は、パスの形(`/lesson/pm-1/`)にする。ブラウザでは、同じコンポーネントが、その HTML を引き継ぐ(ハイドレーション)。教材の本文は、今のとおり、Markdown と TSX の 1 か所だけで書く。
- **根拠(今回の実験)**: ビルドは、すでに 172 レッスンすべてを、Node で HTML に描画している(1.0 秒、合計 1.4 MB)。172 レッスンのブラウザでの引き継ぎは、165 件が警告なしで、7 件に不一致があり、**原因は 7 件とも特定できる、小さな修正**(並べ替え問題のランダムな初期順 4 件、style の数値の桁数 3 件)。アプリ全体の描画は、`useProgress` に 1 行足せば、講座一覧と講座の目次が描画でき、レッスンページは、本文を事前に渡す変更が要る。
- **作者に決めてほしいこと**(§7): 正規 URL の形、旧ハッシュ URL を残す期間、進捗の書き出しに自己診断の回答を含めるか、noindex の対象、など。

### 2.4 公開対象の件数と、リンクの構造(現行データで数え直した)

- 講座 20、ステージ 73、レッスン 172(`catalog.ts`、`curriculum.ts` から。全 20 講座の全段階に本文がある)。
- リンクの構造: 講座一覧 → 講座(カード) → ステージ(講座の目次のカード) → レッスン(ステージのページ)。レッスンからは、前後のレッスン、パンくず、本文中の相互リンク。JS 実行後の DOM では、この経路がすべてハッシュのリンク(`<a href="#/...">`)で存在する。つまり、リンクの構造は、すでにあり、URL の形だけが、検索エンジンに使えない。

- サイトマップに載せる対象(案): 講座一覧 1、地図 1、講座 20、レッスン 172、用語集 1、出典の一覧 1(計 196)。ステージ、ロードマップ、LLM のホームは、案内用の一覧なので、載せない(ただし、クロールの経路としては、生成する)。

### 2.6 進捗の書き出し・読み込み(ドメイン移行の救済に使えるか)

保存の仕組み(コード): 進捗は、`localStorage` の `llm-learning:progress` に、1 つの JSON で保存される(`src/progress.ts`)。自己診断の回答は、別のキー `llm-learning:assessment`(進捗率や書き出しには含めない設計)。API の設定は `llm-learning:api-settings`、API キーは `sessionStorage` の `llm-learning:api-key`(書き出しに含めない設計)。進捗画面に、書き出し(JSON のダウンロード)と、読み込み(JSON のファイル)がある。

実験(Playwright。テスト用のまっさらなプロファイルに、テスト用のデータを置いた。ユーザーのデータは、読んでも、変えてもいない):

| 項目 | 結果 |
|---|---|
| 書き出された内容 | `version`、`completed`(読了)、`quiz`(クイズの最高点)、`questions`(問題ごとの正誤の記録=復習の対象)、`reading`(読み位置)、`lastVisited` |
| 書き出されない内容 | 自己診断の回答(`llm-learning:assessment`)、API の設定、API キー(テストで、ファイルにキー文字列がないことを確認) |
| 別のプロファイルで、画面の「インポート」から読み込む | 進捗が完全に一致した(読了、クイズ、復習の記録、読み位置、最終訪問のすべて)。画面の案内は「進捗を読み込みました。」 |

- 限界: 自己診断の回答は、引き継げない(設計どおり)。**移行で救済できるのは、読了・クイズ・復習・読み位置・最終訪問**。
- `localStorage` は、**オリジン(スキーム+ホスト+ポート)ごと**に分かれる(ウェブの標準の仕組み。今回は実験していない)。パスの形への切り替えは、同じオリジン(`https://shn4pt.github.io`)の中なので、保存データは、そのまま使える(推定。試作で確認する)。**ドメインを変えると、オリジンが変わり、保存データは見えなくなる**。そのとき、書き出し・読み込みが、救済になる。
- 同じオリジン(`shn4pt.github.io`)に、将来、別のプロジェクトのサイトを置く場合、`localStorage` が共有される。キーは `llm-learning:` で始まるので、衝突は、まず起きないが、独自ドメインに移ると、この共有もなくなる。

### 2.8 公式資料から確認した事実(取得日 2026-10-14 UTC。事実と、このサイトへの適用判断を分ける)

| 資料(更新日) | 確認した事実 |
|---|---|
| Google「URL 構造」(2025-12-10) | ページの内容を変えるために、URL のフラグメント(`#/...`)を使わない。Google は、フラグメントを、一般にはサポートしない。JS で内容を変えるなら、History API を使う |
| Google「JavaScript SEO の基本」(2026-03-04) | Google がリンクを見つけられるのは、`href` のある `<a>` 要素。クライアント側のルーティングでは、History API を使い、フラグメントで別のページの内容を読み込まない。JS のページは、クロール → レンダリング → インデックスの 3 段階で処理され、レンダリングは、待ち行列に入る。クライアント側のルーティングの soft 404 を避けるには、404 を返す URL への JS リダイレクトや、`noindex` の追加などを使う。`<title>`、メタの説明、canonical は、JS で設定できる(canonical を、別の URL に変えない) |
| Google「AI 検索機能とサイト」(2025-12-10) | AI Overviews や AI Mode に載るための、追加の要件はなく、特別な最適化も要らない。AI 向けの機械可読ファイル、AI 用のテキストファイル、特別なマークアップも、要らない。特別な schema.org の構造化データも、要らない。構造化データを使うなら、表示されるテキストと合っていること。サポートするリンクとして表示されるには、ページがインデックスされ、スニペット付きで表示できる状態であること |
| Google「サイトマップの作成」(2026-07-08) | サイトマップは、サイトのどこに置いてもよいが、Search Console に送らない限り、置いたディレクトリの下の URL にしか効かない。サイトのルートに置くのが推奨。完全修飾の絶対 URL を使う。1 ファイル 50 MB または 50,000 URL まで |
| Google「robots.txt の作成」(2025-11-21) | robots.txt は、サイトのルート(ホストの直下)に置く。禁止の規則でブロックされていないページは、クロールできるとみなされる |

### 3.3 推奨: A(現行の React / Vite を活かして、ビルド時に全ページの HTML を書き出す)

理由:
1. 教材は静的で、事前に HTML にできる。実際、**ビルドは、すでに 172 レッスンすべてを、1.0 秒で HTML に描画している**。必要なのは、描画結果を、ページごとのファイルに書き出す工程と、ブラウザでの引き継ぎだけ。
2. 変更が、最小限で済む(§5.3 の主要ファイル)。フレームワークの人気を理由に、移行を選ばない。
3. 配信先を変えずに、GitHub Pages のまま、独自ドメインにも対応できる。サーバーの運用が要らない。
4. 本文を二重に書かない(同じ Markdown / TSX から、HTML とアプリの両方が作られる)。

残るリスク: ①ハイドレーションの不一致(E2 で見つかった 7 件、および、ページの枠(進捗、クイズ)の組み合わせで新しく出るもの)。②GitHub Pages の `404.html` が、404 のステータスで配られるか(試作で確認)。③ビルドと CI の時間の増加(未測定)。④将来、ページ数が大きく増えたときの、生成時間(現状 172 レッスンで 1.0 秒なので、当面は問題にならない見込み)。

B に移る理由が、あとから出てくる条件(例): 事前生成スクリプトの保守が、想定より重くなった場合、画像最適化や多言語など、フレームワークの標準の機能が必要になった場合。そのときは、A の成果(パスの URL、メタ情報のデータ、サイトマップ)を引き継げる。

### 4.3 直接アクセス・再読み込み・存在しない URL

- 直接アクセス・再読み込み: 該当のページの HTML が返る(200)。ブラウザは、HTML を引き継ぐ(ハイドレーション)。
- 存在しない URL: GitHub Pages が `404.html` を、404 のステータスで返すように、`404.html` を置く(アプリの殻。`noindex`)。アプリは、未知のルートを、別のページに移動せず、「見つかりません」の表示にする(現行の「ロードマップ」や「講座一覧」への移動は、やめる)。存在しないレッスン ID も、同じ。これで、soft 404 を避ける。**`404.html` が、本当に 404 のステータスで配られるかは、未検証で、試作の受け入れ条件にする**。
- アセットの解決: ベースのパスを絶対にするので、深いパスでも、アセットが解決できる。
- 重複ページ: `/` と `/catalog/` の重複は、canonical で `/catalog/` に寄せる。`index.html` と `/` の重複は、`/` に canonical。ハッシュ付きの旧 URL は、HTTP では `/` と同じ(§4.6)。

### 4.4 ページ別のメタ情報、サイトマップ、検索向けに公開するページ

- **ページ別の title / description / canonical / 共有情報**: 新しいデータは、書かない。既存のデータから、生成する。レッスン: タイトルは、`curriculum.ts` のレッスンの題名と、サイト名(「PM-1 PM の仕事の全体像 | 独習アカデミア」の形)、description は、レッスンの `summary`。講座: `catalog.ts` の講座名と、入口データ(`course-entry.ts`)の「どんな判断に役立つか」。講座一覧、地図なども、同様。canonical と OG の `og:url` は、`SITE_ORIGIN` と `SITE_BASE` から。`og:title`、`og:description` は、title と description と同じ。`og:image` は、画像がないので、第1段階では付けない(画像の用意は、別の判断)。
- **サイトマップ**: ビルド時に、`curriculum.ts` と `catalog.ts` から生成する(§2.4 の対象、196 件)。`<lastmod>` は、`lesson-history.json` の最終コミット日があれば使い、なければ省く(見込みの日付を、書かない)。置き場所は、`<ベース>/sitemap.xml`(Google の資料のとおり、置いたディレクトリの下の URL に効く)。
- **robots.txt**: ホストの直下にしか置けないので、**独自ドメインの決定後**に、`sitemap.xml` の場所の記載とあわせて、置く。いまは、置かない(GitHub Pages のプロジェクト配下では、効かない)。
- **検索向けに公開しないページ**: 進捗、復習、検索、API キーの設定、404 のページは、`<meta name="robots" content="noindex">`(静的ホストでは、HTTP ヘッダを付けられないので、メタタグ)。これらは、ユーザーごとの状態を扱い、検索で見つかる価値がない。内部検索の結果ページは、公開の URL に載せない(検索の索引は、サイト内の機能)。

### 4.5 CSP と構造化データ

- CSP は、**現行のまま維持する**(`script-src 'self'`、`connect-src` は自サイトと Claude API)。検索対応のために、API キーの保護を弱めない。メタタグの CSP も、生成する全ページに付ける(今は `index.html` だけ。ビルドの変換で付く)。
- **構造化データ**: 第1段階では、**入れない**(Claude の設計判断)。Google は、AI 機能への表示に、特別な構造化データを要求しない。必要になれば、E4 のとおり、JSON-LD は CSP の下でも置ける(データのブロック)。入れるなら、表示される内容と合うものに限る(例: 講座の名前と説明。本文と合わない主張を入れない)。
- 旧リンクの転送などの、実行する JS は、**インラインにせず、外部ファイル**(`<ベース>/assets/` のスクリプト)にする(E4)。

### 4.6 旧リンク(`#/lesson/pm-1` など)の救済

- フラグメントは、サーバーに送られない(MDN)ので、**サーバーの転送だけでは、教材ごとの移転は完了しない**。旧リンクは、HTTP では `/dokushu-academia/`(ルートの HTML)を取得する。
- 提案: ルートの `index.html`(と、全ページの殻)に、小さな外部スクリプトを読み込み、**`location.hash` が `#/` で始まる場合だけ**、パスの URL(`<ベース>/<path>/`)へ `location.replace` で移す。たとえば `#/lesson/pm-1` → `/dokushu-academia/lesson/pm-1/`。存在しない ID は、講座一覧へ移す。JS が実行されない環境では、ルートの HTML(講座一覧と同じ内容)が見える。
- 限界: 旧ハッシュ URL を、検索エンジンが、教材ごとの別 URL として登録しているとは想定しない(Google は、フラグメントをサポートしない)。外部に出回った旧リンクが、JS を実行するブラウザで、新 URL に移る、という救済で、検索の評価の引き継ぎは、期待しない。
- この転送を残す期間は、**作者の判断**(§7)。短く切るほど、保守が軽く、長く残すほど、旧リンクが生きる。

### 4.7 ドメイン変更時の `localStorage`、書き出し・読み込み、切り戻し

- **パスの URL への切り替え**(同じ `https://shn4pt.github.io` の中): 保存データは、そのまま使える見込み(オリジンが同じ。試作で確認する)。
- **独自ドメインへの移行**: オリジンが変わり、保存データは見えなくなる。救済は、既存の「エクスポート」→新ドメインで「インポート」(§2.6 の実験で、読了・クイズ・復習・読み位置・最終訪問が復元できることを確認済み)。
  - 案: 旧ドメイン側の進捗画面(と、講座一覧の上部)に、移行の案内と、エクスポートへの導線を、一定期間表示する。案内の文面は、独自ドメインが決まってから書く。
  - 限界: 自己診断の回答は、書き出しに含まれない(設計)。含めるかは、作者の判断(§7)。API の設定と API キーは、含めない(設計どおり。再入力が要る)。
- **切り戻し**: 事前生成とパスの URL は、リポジトリの `main` に入れるので、問題があれば、`git revert` で、前のビルド(ハッシュの URL)に戻せる。独自ドメインへの移行は、DNS の変更で、元の `github.io` の URL に戻せる(GitHub の手順に従う。設定の詳細は、ドメイン決定の段階の調査で扱う)。

### 4.8 ドメインが未定でも進められる試作の範囲と、決定後に変える設定

- 進められる: パスの URL、ビルド時の事前生成、ハイドレーション、ページ別メタ情報、サイトマップ、404、旧ハッシュの転送、`noindex`。ドメイン未定の間は、`SITE_BASE=/dokushu-academia/`、`SITE_ORIGIN=https://shn4pt.github.io` で動かす。
- 決定後に、設定だけで変える: `SITE_BASE`(`/`)、`SITE_ORIGIN`(新ドメイン)、`CNAME`、robots.txt(ホスト直下)の追加、canonical とサイトマップの再生成、Search Console の登録、旧ドメインからの案内。

### 5.4 旧リンク・進捗の検証方法(試作)

- 旧リンク: 旧形式のハッシュ URL(`/#/lesson/pm-1`、`/#/course/pm`、`/#/catalog`、存在しない ID)を開いて、移動先を確認する(Playwright)。
- 進捗: テスト用のまっさらなプロファイルで、①保存データを作る、②パスの URL に移動して、同じデータが読める、③エクスポート → 別のプロファイルでインポート、で復元できる。ユーザーのデータは、使わない。

## 6. 作業量の粗い見積もりと、不確かさ

期日や成功率は、約束しない。「作業」は、Claude Code の実作業の目安で、作者のレビューと確認の往復(作者の確認は、週に数時間の想定)を含まない。**実際は、レビューの往復が、所要の中心になる見込み**。

| 段階 | PR の数の目安 | 実作業の目安 | 不確かさ |
|---|---|---|---|
| 試作(§5 の 3 ページ+共通の基盤) | 2〜3 本 | 数時間〜十数時間 | **中**。ハイドレーション、GitHub Pages の 404、ベースのパスの切り替えの、未知の問題による。E2 で既知の 7 件は、小さい |
| 全教材への展開(172 レッスン、20 講座、73 ステージ、メタ情報、サイトマップ) | 2〜3 本 | 数時間〜十数時間 | **小〜中**。試作で型ができていれば、機械的。ただし、ハイドレーションの不一致が、組み合わせで増える可能性。CI の時間の増加は、未測定 |
| 移行(独自ドメイン、旧リンクの案内、Search Console、計測) | 1〜2 本+作者の作業(DNS、アカウント) | 数時間+作者の作業 | **大**。ドメインが未定で、費用・取得可否・DNS の設定は、作者の作業と判断に依存する。この見積もりは、候補の調査後に、見直す |

見積もりの根拠: 変更点の数(§2.3 の、「1 つの正規表現」「1 つの関数」「1 行」で足りる箇所の多さ)と、E1・E2・E3 の実測。根拠が弱いところ: ビルド・CI の時間、GitHub Pages の `404.html` の挙動、ハイドレーションの、枠(進捗・クイズ)を含む全体での挙動(E2 は、本文だけ)。

## 7. 作者に決めてもらう事項と、Claude が設計判断で解決した事項

### 7.1 作者に決めてもらう事項

1. **正規 URL の形**: パスの形(`/lesson/pm-1/`、末尾にスラッシュ、`/` は `/catalog/` に canonical)でよいか。
2. **旧ハッシュ URL の転送を残す期間**: 短く切る(例: 次の独自ドメイン移行まで)か、長く残すか。期間の根拠は、出せない(外部に出回った旧リンクの数が、未確認のため)。
3. **進捗の書き出しに、自己診断の回答を含めるか**(いまは含まない設計)。含めるなら、進捗のコードと、書き出しの形式の変更になる(別の小さな Issue)。
4. **`noindex` の対象**: 検索、復習、進捗、API キーの設定、404 でよいか。
5. **共有用の画像(`og:image`)**: 第1段階では付けない案。ブランドに関わるので、必要なら、作者が方針を決める。
6. **独自ドメイン**: 候補は未定。調査(候補 3〜5 案、取得可否の確認日時、初年度と更新の費用、移行手順)は、次の段階で別に行う(今回は、対象外)。

### 7.2 Claude が設計判断で解決した事項(異論があれば、変更する)

- 方式は、A(現行を活かしたビルド時の事前生成)。
- ルーターは `BrowserRouter`(`basename` はビルド時の設定)。`base: './'` は廃止し、絶対のベースにする。
- 事前生成は、アプリと同じコンポーネントを使い、ブラウザでは引き継ぐ(ハイドレーション)。ページ別のメタ情報は、既存のデータから生成する(新しいデータを書かない)。
- 存在しない URL は、`404.html`(404 のステータス)と「見つかりません」の表示にする(soft 404 を避ける)。
- サイトマップは、196 件(講座一覧、地図、講座、レッスン、用語集、出典の一覧)。ステージ、ロードマップ、LLM のホームは、生成するが、サイトマップには載せない。
- robots.txt は、独自ドメインの決定後に、ホスト直下へ置く。いまは置かない。
- CSP は維持する。JSON-LD は、第1段階では入れない。入れる場合は、データのブロックなので、CSP の下で動く(E4)。実行するスクリプトは、外部ファイルにする。
- AEO 専用のファイルや特別なマークアップは、作らない(Google の資料に、必要ないとある。OpenAI の資料でも、robots.txt のタグだけが、管理の手段として挙げられている)。
- 教材を、検索のために薄くしない。生成する HTML は、アプリと同じ本文(出典、限界、問い)を、そのまま含む。
