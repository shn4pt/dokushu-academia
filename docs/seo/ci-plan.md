# CI の実行条件と分数の見直し案(Issue #32)

`docs/seo/rollout.md` §4.4・§4.5 の CI 計画を、具体化した**設計案**。**workflow(`.github/workflows/`)は、変更していない。** 草案は `docs/seo/ci-plan-draft/` に置いた(適用していない)。分類のスクリプト(`scripts/ci-classify.mjs`)は、ローカルの検証用で、workflow には、つないでいない。GitHub の設定(必須チェック、支払い、保護)の操作、全 172 教材の生成・診断、外部配信、アカウント作成、契約、購入、DNS、権限付与、private 化は、していない。**デプロイ前の検査の削減は、提案であり、実装・適用済みではない。**

## 0. 要約

- **推奨案**: 変更を分類し、**文書だけと確定できたときだけ**、重い手順(ビルド・テスト)と配信を省く。**ジョブは、従来と同じ名前(`test`)の 1 つのまま**にし、workflow ごとは省かない(`paths-ignore` は、必須チェックが Pending のままになるため。公式資料)。
- **期待される効果(測定した割合からの推定)**: 文書だけの PR の CI は、7 分 → 約 1 分。文書だけの main への push のデプロイは、8 分 → 約 1 分。月の分数は、**約 27〜29% 減**(§6)。**ただし、直近の開発ペースが続くと、それでも月 2,000 分を超える**。回数の運用(まとめて push する)が、さらに必要。
- **PR で通ったコード = 公開するコード**: 直近の 4 件のマージで、PR の検査を通した木(ファイルの内容)と、main に入った木を比べると、**2 件は同一、2 件は文書のメモ 1 ファイルだけの差**(推定した統合木の再構成。§4)。完全な一致を、機械的に保証する仕組みは、まだない。main で完全な検査をやめる案(B)は、今回は、推奨しない(§4)。
- **作者の判断が要ること**(§10): 文書だけの変更で、検査を省くことの採否。workflow の変更の承認。超過時の扱い。

## 1. 現状と実測(PR #28 のレビューで統一した値)

**workflow の構成(現在)**
- `ci.yml`: `pull_request` と `workflow_call`。ジョブは `test` の 1 つ(約 15 ステップ)。
- `deploy.yml`: `push`(main)。`test`(`ci.yml` を呼び出す)→ `build` → `deploy` の 3 ジョブ。workflow 全体に `concurrency: pages`(`cancel-in-progress: true`)。

**実測**(GitHub の記録。2026-10-15〜17 取得)
- 1 回の CI の `test` ジョブ: **387 秒(約 6.5 分)**。内訳は、`npx playwright test` が 319 秒(1,018 件。[run 38667805700](https://github.com/shn4pt/dokushu-academia/actions/runs/38667805700)、head 4473b6f)。その後、公開文書などで、全体が増えた(最新の run では、約 1,105 件、約 4.7 分のステップ)。
- 課金は、ジョブごとに、分へ切り上げ: PR の CI = 7 分、デプロイ = 8 分(`test` 6 + `build` 1 + `deploy` 1。**CI は、その後、少し伸びたので、実際は 8〜9 分**)。
- **文書だけの変更の割合(実測)**。分類は、`scripts/ci-classify.mjs` の規則(§2)。
  - マージされた PR 16 件のうち、**文書だけは 5 件(31%)**、それ以外は 11 件。
  - PR の CI の実行 38 回のうち、文書だけの PR のブランチのものが **15 回(39%)**。課金の分数では、237 分のうち 91 分(38%)。
  - main への push(デプロイ)の実行 146 回のうち、**文書だけの変更のものが 34 回(23%)**。
  - **どちらも、開発が集中した期間(2026-10-07〜17)の値で、運営の平常時の値ではない**。文書の PR(設計・調査)が多かった期間なので、**割合は、偏っている**(平常時は、低い可能性)。

## 2. 変更の分類と、実行する検査

分類の規則(`scripts/ci-classify.mjs`。**安全側**: 「文書だけ」と確定できたときだけ、省く)

| 分類 | 対象 | 実行 |
|---|---|---|
| **文書だけ** | `docs/**`(下の例外を除く)、`reviews/**`、`README.md` | **完全な検査を省く**。公開用の `dist/` は変わらないので、**配信も省く** |
| **検査が読む文書(例外)** | `LICENSE`、`LICENSE-CONTENT.md`、`docs/licenses.md` | **完全な検査**(公開文書の生成と、テストが、これらを読む。文書に見えても、入力) |
| **コード・データ・教材・設定** | `src/**`、`scripts/**`、`e2e/**`、`package*.json`、`vite.config.ts`、`playwright.config.ts`、`tsconfig.json`、`index.html` ほか | **完全な検査** |
| **workflow** | `.github/workflows/**` | **完全な検査**(検査の仕組み自体が変わる) |
| **未知のパス・空の一覧・取得の失敗** | 上のどれでもないもの | **完全な検査**(安全側) |

- 文書とコードが混ざった PR は、完全な検査。
- **検査が読む文書の一覧は、実際の読み取りと照合する**(`vite.config.ts` が読むファイルが、一覧にあることを、テストで確認)。新しく、文書を読む検査・ビルドを足したら、この一覧に足す(**足し忘れの危険**: 一覧にないと、その文書だけの変更で、検査が省かれる)。
- **完全な診断(全 172 教材、Issue #33 の B)は、毎回の PR では行わない**(作者の別の承認が要る。草案には、含めていない)。

## 3. 必須チェックが「永遠に pending」にならない設計

- **公式資料(2026-10-17 取得)**: workflow が、ブランチ・パスのフィルター(`paths`・`paths-ignore`)・コミットメッセージで、**省略された場合、その workflow のチェックは、「Pending」のまま残り**、必須にしている PR は、マージできなくなる。
- したがって、**workflow ごとは省かない**。常に、ジョブ `test` が実行され、中の**ステップを、分類の結果で、省く**。ジョブの結果は、省略したときも、成功と決まる(**ジョブ名は、従来と同じ `test` のまま**。必須チェックの設定が、あれば、変更が要らない)。
- **「省略した」と「実行して成功」を、区別**する: ステップのサマリー(`$GITHUB_STEP_SUMMARY`)に、「完全な検査を省略(文書だけの変更)」と、分類の結果(理由)を、書く。ログに、残る。
- **失敗と取り消しは、成功に見せない**: 重いステップの失敗は、ジョブの失敗。同じ PR の古い実行の取り消しは、取り消し(成功ではない)。**取り消しの設定は、PR の実行だけ**(`cancel-in-progress: ${{ github.event_name == 'pull_request' }}`)。main の実行(公開用)は、取り消さない。**ただし、`cancel-in-progress: false` だけでは足りない**(PR #35 のレビュー指摘。GitHub 公式の concurrency 仕様): 同じ group では、実行中は 1 つ、**待機は 1 つだけ**で、新しい実行が、古い**待機中**の実行を置き換える(取り消す)。「A の検査中 → コード B が待機 → 文書だけの C」で、B が取り消され、C は(直前の B との差が文書だけなので)ビルド・配信を省くと、**B のコードが、検査も配信もされない**。そのため、**main の実行は、実行ごとに別の group**(`github.run_id`)にして、待機中の置き換えをなくす(草案 `ci.yml`)。
- **ジョブを足さない**: 別の「分類」ジョブ、「結果」ジョブを足すと、ジョブごとに 1 分に切り上げて課金される(文書だけの PR が、2〜3 分になる)。1 つのジョブの中の最初のステップで、分類する。**ただし、`deploy.yml` の `test` は、再利用 workflow の呼び出しなので、分類の結果を出力(`full`)で受けて、`build`・`deploy` を省く**。
- 草案: `docs/seo/ci-plan-draft/ci.yml`、`deploy.yml`(YAML の構文は、Ruby の YAML で確認した。**Actions での実行は、していない**)。

## 4. PR で通ったコードと、公開するコード

**仕組み**: PR の CI は、**PR の head と、その時点の base(main)を、統合した、仮の統合コミット**を検査する。マージ(squash)後に、main に、新しいコミットができ、`deploy.yml` が、それを、もう一度、検査して、配信する。

**実測(推定した統合木の再構成による比較)**: 4 件のマージ(#26・#27・#28・#34)について、「PR の最後の CI が検査した木(base + head の統合)」を、**`git merge-tree` で再構成**し、「main に入った木」と比べた。**実際の CI の統合コミットを確認したものではない**(GitHub が作る仮の統合コミットの SHA は、再取得できない)。base は、**最後の CI の開始時刻(UTC)以前の、main の先頭と推定**した。

| PR | head(最後の CI) | 推定 base(main の先頭) | main に入ったコミット | 再構成した木 | main の木 | 結果 |
|---|---|---|---|---|---|---|
| #26 | 733d008 | a859f7e | c04ce18 | 8d5c7ca | 6cf6b1d | 差は `docs/memory/project-pm1-pilot-and-review-flow.md` だけ |
| #27 | 39b6bb2 | c04ce18 | eb2298f | 1147d3d | 1147d3d | **同一** |
| #28 | 06bde38 | eb2298f | 97f1130 | f8b3f57 | f8b3f57 | **同一** |
| #34 | 895d57a | 97f1130 | 9048f55 | 0c405cd | a04a1ac | 差は `docs/memory/project-pm1-pilot-and-review-flow.md` だけ |

差の 2 件は、PR の CI の後に、**文書だけの変更が main へ直接入った**ため(#26: e22cf28 の記憶の写しの更新、#34: df4d0a7)。**(この表は、レビュー指摘で、SHA を記録して作り直した。前の版は「3 件同一・1 件差」と書いたが、base の推定を揃えて再計算すると、「2 件同一・2 件が docs/memory だけの差」。いずれも、コードの差はない)**

追試の手順(各行):
```
base=$(git rev-list -1 --first-parent --until="<最後の CI の開始時刻 UTC>" origin/main)
git merge-tree --write-tree "$base" <head>       # 再構成した木(1 行目)
git rev-parse <main に入ったコミット>^{tree}       # main の木
git diff --name-only <再構成した木> <main の木>    # 差
```
CI の開始時刻: #26 05:26:43Z(run 39006277908)、#27 05:57:19Z(39008117596)、#28 06:05:38Z(39008632702)、#34 06:46:58Z(39011180093)。(**限界**: 4 件だけ。base の推定は、時刻による。)

**案**
- **A(推奨・第一段階)**: 分類(§2)だけ。main の検査は、コード変更では、完全のまま。**公開の安全の水準は、下がらない**。省くのは、文書だけの変更。
- **B(今回は推奨しない)**: main で、「PR で検査した木と、同一(または差が文書だけ)」なら、完全な検査を省く。コード変更のデプロイの分数を、さらに減らせる(§6 の試算)。**ただし**: ①検査した木を、機械的に記録・照合する仕組み(Artifact や API の読み取り、`actions: read` の権限)が要る。②「PR の検査結果」と「main の木」の対応づけを、誤ると、**未検査の main を公開する**。③上の実測は、4 件だけ。④「デプロイ前の検査の削減」は、作者の安全基準の判断。**実装の前に、小さな実験(ブランチで、記録と照合を試す)が要る**。
- **C(不採用)**: main の検査を、常に省く(PR で通ったので)。**マージ差分・依存・生成物が違うのに、「二重実行」とみなして省く**ことになり、未検査の main を公開しうる。
- 「同じ SHA」ではなく、**木**で比べる理由: squash マージでは、コミットの SHA が必ず変わる。

## 5. main への push と配信

- 文書だけの変更で、**配信を省く**: 公開用の `dist/` は、文書では、変わらない(**ただし、ライセンス類は、公開文書の入力なので、例外(§2)**)。
- **基準 = 最後に配信に成功したコミット**(`github-pages` の deployment の記録を、API で読む。`deployments: read`)。直前の push(`github.event.before`)**ではない**: 検査・配信されなかったコード(取り消し・失敗・配信の省略)が、あいだに入っていても、その差が含まれるので、見落とさない。基準を取得できない・存在しない・**祖先でない(強制 push など)**場合は、**完全な検査(安全側)**。
- **順序の逆転を防ぐ**: main の実行は並列になりうるので、古い実行が、新しい実行より後に配信すると、旧版が公開される。`build` ジョブの最初のステップで、「この実行の SHA が main の先頭か」を確認し、**先頭でなければ、`deploy` ジョブごと省く**(新しい実行が、基準=最後の配信なので、差を含めて配信する)。**ステップではなくジョブごと省く理由**: `environment` 付きのジョブは、実行すると、そのコミットを「配信済み」と記録し、基準が狂う。確認に失敗した場合は、配信する側に倒す。
- **配信は取り消さない**(`group: pages`、`cancel-in-progress: false`)。待機中の古い配信は、新しい実行に置き換えられるが、基準が最後の配信なので、新しい実行が差を含む。**配信のジョブだけに**付ける(文書だけの実行が、配信を取り消さないように。従来は、workflow 全体に付いていた)。
- **残る限界**: 先頭の確認と配信のあいだの、短い競合(配信自体は、`group: pages` で直列)。新しい実行の検査が失敗すると、その間、古い実行のコードも配信されない(従来も同じ)。
- **既知の限界**: 文書だけの変更を、配信しないので、「公開中のサイト = 最新の main」ではなくなる(文書だけの差なので、サイトの表示は、変わらない)。

## 6. 分数の試算

**式**: 月の分数 = PR の CI 回数 × 1 回の分数 + main へのデプロイ回数 × 1 回の分数(`rollout.md` §4.4)。**課金は、ジョブごとに、分へ切り上げ**。

**1 回の分数**(実績ベース。**実測と推定を分ける**)
| | 現在(過去の実測を使うモデル値) | 提案(A)の推定 |
|---|---|---|
| PR の CI(文書だけ) | 7 分 | **約 1 分**(分類のステップのみ。checkout + node + 分類。推定) |
| PR の CI(コード等) | 7 分 | 7 分(分類のステップは、数秒。ジョブは、同じ 1 つ) |
| デプロイ(文書だけ) | 8 分 | **約 1 分**(`test`(分類のみ)。`build`・`deploy` は、省略) |
| デプロイ(コード等) | 8 分 | 8 分 |

**文書だけの割合**: PR の CI は **p = 0.39**、デプロイは **q = 0.23**(§1。**偏りあり**)。
- 提案の平均: PR = 0.39×1 + 0.61×7 = **4.66 分**、デプロイ = 0.23×1 + 0.77×8 = **6.39 分**。

| ケース(回数/月) | 現在の組み立て | 提案(A) | 減り方 |
|---|---|---|---|
| 運営の平常(**仮定**。PR 8、デプロイ 8) | 8×7 + 8×8 = **120 分** | 8×4.66 + 8×6.39 = **約 88 分** | −27% |
| 中間(**仮定**。PR 30、デプロイ 20) | 370 分 | 30×4.66 + 20×6.39 = **約 268 分** | −28% |
| 2026-10-13〜15 の実績の延長(**実測の回数**。PR 約 500、デプロイ約 220) | 5,260 分 | 500×4.66 + 220×6.39 = **約 3,736 分** | −29%(**2,000 分を超える**) |

- **B を足した場合(参考。推定。同一の木の割合を 2/4 と仮定)**: コード変更のデプロイ = 0.5×3 + 0.5×8 = 5.5 分(分類 + ビルド + 配信)。デプロイの平均 = 0.23×1 + 0.77×5.5 = **約 4.5 分** → 平常 約 73 分、中間 約 230 分、実績の延長 約 3,300 分。**実績の延長では、B でも、2,000 分を超える**。
- **2,000 分に収まる回数の目安**(比 PR : デプロイ ≒ 500 : 220 のとき): 提案(A)で、**PR 約 268 回/月(約 9 回/日)+デプロイ 約 118 回**。現在の組み立てでは、**PR 約 190 回(約 6 回/日)**。**回数の運用(変更をまとめて push する、WIP を push しない)が、技術的な削減と同じくらい効く**。
- **含めていないもの**: 同じ PR の古い実行の取り消しによる削減(デプロイで取り消されたのは 139 回中 9 回。PR の分は、記録なし)、再実行・失敗の分、artifact の保管などの別枠(GitHub の公式資料で、別枠として示されている。**数値は、この文書では確認していない**)。**所有者のアカウントの無料枠(月 2,000 分)は、このリポジトリ専用ではなく、ほかの private リポジトリと共有**。
- **現行の Pages の実時間を、将来の Cloudflare 向けの Actions の仮定に使う場合は、同一の請求実績ではない**(`rollout.md` §4.4)。**private 化の前は、公開リポジトリで、課金されていない**。

## 7. 秘密・fork・超過時

- **fork からの PR に、秘密を渡さない**: 現在の workflow は、秘密を使わない(`permissions: contents: read` のみ。`pull_request` イベント)。草案も、同じ。`pull_request_target` は、使わない。
- **公開リポジトリへ移して、private の資産を逃がす案は、採らない**(private 資産を公開しない)。
- **超過時**: 追加の課金を、**自動で承認しない**。GitHub の支払い・予算の設定は、**作者の操作**で、この文書は、設定しない。方針の選択肢(作者が決める): ①超過したら、PR の検査を止めて、手元で検査し、成果物だけを手動で配信する(`rollout.md` §8)。②予算の上限を決めて、その範囲で、追加購入する。③回数の運用で、枠内に収める。

## 8. 失敗・取り消しの検査(どう確かめるか)

**ローカルで確認済み**(`e2e/ci-classify.spec.ts` 13 件、ブラウザなし)
- **実際の Git の差分**(一時リポジトリ。PR #35 のレビュー指摘): コード→docs の移動、`docs/licenses.md`→別の docs の移動、コードの削除は**完全**、docs→docs の移動だけは**省く**。既定の `git diff --name-only` は、移動で、移動先だけを返すため、`--no-renames` を使う(使わないと、前 2 件の検査が失敗することを確認した)。
- **検査が読む文書の自動発見**: `vite.config.ts`・`e2e/*.ts`・`scripts/*.mjs` の `readFileSync('docs/…' | 'reviews/…' | README | LICENSE…)` を探し、見つかったものが、すべて完全な検査になる(動的なパスは、見つけられない)。草案(`docs/seo/ci-plan-draft/`)は、検査が構造を読むので、**完全な検査の対象**にした(例外の一覧 `CONSUMED_PREFIX`)。
- 文書だけは省き、配信も省く。ライセンス類(`LICENSE`・`LICENSE-CONTENT.md`・`docs/licenses.md`)、コード・データ・教材・設定・テスト・スクリプト、混在は、完全。workflow の変更は、完全で、理由に明示。空の一覧・未知のパス・名前の揺れ(`docs`・`docsx/`・大文字小文字)は、安全側。
- **検査が読む文書の一覧の整合**(`vite.config.ts` の読み取りと照合)。
- 草案の構造: ジョブ名が `test` の 1 つ、`paths-ignore`・`paths` を使わない、PR だけ取り消す、`^0+$`(前の基準がない場合)、重い手順がすべて分類に従う、`concurrency` は配信ジョブだけ。YAML の構文は、Ruby で確認。
- **過去の 16 件のマージ PR と、146 件のデプロイを、分類**した(§1。割合の根拠)。

## 9. 切り戻しと、残る設定

- **切り戻し**: workflow の変更を、`git revert` で戻す(変更前の `ci.yml`・`deploy.yml` に戻る)。分類のスクリプトと、草案は、workflow から参照されないので、残っても影響しない。
