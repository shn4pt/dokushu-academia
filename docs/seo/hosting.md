## 0. 要約

- **推奨案(1 つ)**: **Cloudflare の静的配信(Free プラン。第一候補は、新しいプロジェクトに推奨されている Workers の静的アセット。Pages は、同等の挙動を確認できた代替)**に、**GitHub Free の private リポジトリ**から、**GitHub Actions でビルドして、成果物をアップロード**して配る。Cloudflare に、ソースの読み取り権限を渡さない。静的アセットへの要求は、Free でも無料・無制限(公式)で、月の予算を使い切って、サイトが止まる仕組みがない。
- **ただし、契約・移行の前に、確認が要る点が残る**(§10): Cloudflare の利用規約のうち、**Free のサービスを受ける Web 資産で、カード情報を処理・収集してはならない**(公式、2.2.1(h))点は、「外部の決済サービスへのリンクだけにして、自サイトでカード情報を扱わない」設計と両立するはずだが、**個別の適合は、確認していない**。「Free は、Cloudflare の裁量で終了できる」(2.6)ことも、リスク。商用の可否は、「禁止が見つからなかった」だけで、許可の確認にはしていない。
- **代替**: Netlify Personal(月 9 USD、1,000 クレジット)。**Netlify Free は、クレジットを使い切ると、すべてのプロジェクトが停止する**(ハードリミット)ので、本番の配信先に向かない。本番デプロイ 1 回が 15 クレジットで、月 20 回で、無料枠を使い切る。Vercel Hobby は、非商用・個人利用に限るので、除外。GitHub の有料プラン + Pages は、**プランだけで、Pages の商取引の制限が解除される、とは想定しない**ので、基準の比較用。
- **旧サイト・進捗の救済の推奨**: **現行の公開リポジトリを、旧サイトの移行・案内用に、公開のまま残し、今後の開発を、新しい private リポジトリへ移す**(§5)。旧 URL(`/dokushu-academia/…`)、同じオリジン(`localStorage` の進捗)、出典・ライセンス・更新記録・報告先の、4 種類の GitHub へのリンクが、そのまま使える。**自動転送は、保存済みの進捗がないときだけ**にして、進捗があるときは、書き出しの案内を先に出す。**本番移行前に、必ず検証する項目を、§10 に挙げた**。
- **作者に決めてほしいこと**(§9): 継続費用の上限、新しい private リポジトリの作成と、Cloudflare のアカウント作成(作者の作業)、公開範囲、移行の時期。技術的な選択肢の比較は、この文書で行った。

### 3.3 配信の機能(ローカルのエミュレータの結果。**本番の確認ではない**)

PR #17 の出力(`dist-path-root`。ベース `/`)を、各ツールで配った。`404.html`、`_headers`(CSP と、`/assets/*` の長期キャッシュ)を入れた。

| URL | `wrangler pages dev`(Pages) | `wrangler dev`(Workers 静的アセット。`html_handling: auto-trailing-slash`、`not_found_handling: 404-page`) | `netlify dev`(`--dir`) | GitHub Pages(PR #17 の配信の再現。**実物ではない**) |
|---|---|---|---|---|
| `/lesson/pm-1/` | 200 | 200 | 200 | 200 |
| `/lesson/pm-1`(スラッシュなし) | **308** → スラッシュ付き | **307** → スラッシュ付き | **200**(転送なし) | 301 → スラッシュ付き |
| `/lesson/pm-1/index.html` | 308 → ディレクトリ | 307 → ディレクトリ | 200 | 200 |
| `/lesson/pm-2/`(生成していない)、`/nothing/` | **404**(`404.html`) | **404**(`404.html`) | **404**(`404.html`) | 404(`404.html`) |
| `/404.html` | 308 → `/404` | 307 → `/404` | 200 | 200 |
| `/sitemap.xml` | 200 | 200 | 200 | 200 |
| `/robots.txt`(置かない) | 404 | 404 | (未確認) | 404 |
| `_headers` の CSP | **HTTP ヘッダーで付く**(404 の応答にも) | 付く | 付く | **付けられない**(メタタグのみ。観察: 200 の応答に CSP ヘッダーなし) |

- **判断に使える点**: ①どの候補でも、`404.html` を置けば、存在しないパスは、**404 のステータス**で、殻が返る(SPA の全 URL に 200 を返さない)。②Cloudflare は、`404.html` を置かないと、SPA として、ルートを 200 で返す(公式)ので、**`404.html` を、必ず置く**。③**HTTP ヘッダーの CSP**(`_headers`)を使える(GitHub Pages は、メタタグだけ)。`frame-ancestors` など、メタタグでは効かない指示も、使える。④スラッシュなしのパスの扱いは、配信先で違う: Cloudflare は転送する(**Pages は 308、Workers は 307 だった。本番のステータスは、未確認**)。Netlify は、**ローカルでは転送せず**、スラッシュなしでも 200(本番の挙動は、未確認。重複 URL になるので、canonical が必要)。**内部リンクを、最初から、スラッシュ付きで出す**(PR #17 の限界として挙げた、`Link` の包み方)と、転送の違いに、依存しなくて済む。
- **ベースのパス**: Cloudflare・Netlify は、プロジェクトを、ドメインのルートで配る(`*.pages.dev`、`*.workers.dev`、`*.netlify.app`、独自ドメイン)。**ルート配下のビルド(`build:path:root`)**を使う。プロジェクト配下(`/dokushu-academia/`)で配る必要はない。
- robots.txt・サイトマップは、ルートに置ける。独自ドメインなら、ホストの直下。`*.pages.dev` などの、共有ドメインでは、自分のサイトの直下であり、置けるが、独自ドメインの前の、評価の引き継ぎは、別問題。

### 3.4 接続方式の比較: Git 連携と、GitHub Actions からのアップロード(個人所有の private リポジトリ)

| | Git 連携(配信先が、リポジトリを読む) | GitHub Actions でビルドし、成果物をアップロード(Direct Upload / CLI) |
|---|---|---|
| 必要な権限 | 配信先の GitHub アプリに、リポジトリの読み取り(と、状態・コメントの書き込み)。リポジトリを選んで、絞れる(Cloudflare) | 配信先の **API トークン**(最小の権限)と、アカウント ID を、GitHub のシークレットに置く。**配信先に、ソースを読ませない** |
| 初期設定 | 配信先でプロジェクトを作成し、リポジトリを連携 | ワークフローに `wrangler pages deploy`(または `wrangler deploy`)を足す。プロジェクトは、配信先で、先に作る |
| ビルドの場所と枠 | 配信先(Cloudflare Pages の Git 連携の枠: 月 500 回、20 分まで。Workers の枠は未確認) | GitHub Actions(private: Free で 月 2,000 分)。既存の CI が、すでにビルド・テストをしている |
| プレビュー | プルリクエストごとに、自動(Cloudflare は、無制限) | ブランチ名を指定してデプロイ(自分で組む)。**プレビューを検索に出さない設定は、未確認** |
| 切り戻し | 配信先の管理画面で、前のデプロイへ(未確認) | 前の成果物を、再アップロード。Git の `revert` で、再ビルド |
| private 化後の CI 枠 | 配信先のビルド枠 | **GitHub の分数**。現在の CI は、1 回 4〜6 分(観察: 4 分 3 秒〜5 分 44 秒。パス版のビルドを足すと、少し増える見込み) |
| ソースの扱い | 配信先に、private のソースが、渡る | 渡らない(成果物だけが渡る。成果物は、公開される HTML・JS) |

**推奨は、GitHub Actions からのアップロード**(理由は、§4)。

## 4. 推奨案と理由

**Cloudflare の静的配信(Free)+ GitHub Free の private リポジトリ + GitHub Actions からのアップロード。**

理由:
1. **静的配信の料金枠の使い切りによる停止がない**。静的アセットへの要求が、無料・無制限(公式)。Netlify Free のように、月の予算を使い切って、サイト全体が止まることがない。**前提は「Worker のスクリプトを実行しない静的配信」**。Worker の実行は別枠で、`run_worker_first` などで実行すると、Free の上限で 429 になりうる(公式)。将来、API などを足すときは、再見積もりする。規約による終了のリスクは別(2.6)。認知拡大の目的(検索・AI から見つかること)に合う。
2. **ソースを、配信先に渡さない**。private 化の目的(将来の開発・有料商品・運営情報を守る)に合う。成果物(公開される HTML・JS・無料本文)だけを渡す。
3. **既存の CI を、そのまま使える**。ビルド・テストは、すでに GitHub Actions にある。private 化後も、Free の月 2,000 分に収まる見込み。
4. **配信の機能が、設計と合う**: `404.html` で 404 のステータス、HTTP ヘッダーの CSP(`_headers`)、ディレクトリの `index.html`、ルート配下のベース。プレビューは、無制限(Pages)。
5. **費用が予測しやすい**: 配信は 0 USD。月額の追加費用が、ドメイン以外にない(試算の範囲)。

**Workers か Pages か**: Cloudflare の公式資料は、新しいプロジェクトに、Workers を推奨している(Pages の概要、2026-08-25 更新)。静的アセットの Workers は、`html_handling` と `not_found_handling` を設定でき、ローカルの実験でも、Pages と同じく、`404.html` が 404 で返った。**推奨は Workers の静的アセット**とし、Pages は、同等に動いた代替とする。**どちらを選ぶかは、本番移行前の、実際のプレビューでの検証後に、決める**(Pages の資料に、廃止の予告は、取得した範囲では見つからなかった)。

**残るリスク**:
- **規約**: Free のサービスを受ける Web 資産で、**カード情報を処理・収集してはならない**(2.2.1(h))。将来の販売は、外部の決済サービスへのリンク(購入は、決済サービスのページで行う)に限り、自サイトに、カード番号の入力欄を置かない。**この設計が、規約に合うことは、確認していない**(§11 の質問案)。**Free のサービスは、Cloudflare の裁量で、終了できる**(2.6)。事業の重要な収入源になる前に、有料プランへの移行と、別の配信先への切り替えの手順を用意しておく。商用の可否は、**「禁止が見つからなかった」だけで、確認済みとしない**。
- **独自ドメイン**: **Workers の Custom Domains は、apex でもサブドメインでも、Cloudflare の有効なゾーンが要る**([Workers Custom Domains](https://developers.cloudflare.com/workers/configuration/routing/custom-domains/)。Codex のレビューが確認した内容で、Claude は再取得していない)。Pages は、外部 DNS のサブドメインに CNAME を向ける経路がある(Pages の資料)。この可能性を、Workers に当てはめない。ドメイン調査と、一緒に決める。Workers と Pages の違いは、下の小表のとおり。
- **転送のステータス**: ローカルでは、Pages が 308、Workers が 307。**本番のステータスは、未確認**。内部リンクを、スラッシュ付きで出すことで、依存を減らす。
- **API トークン**: GitHub のシークレットに置く。**選んだ方式(Workers か Pages)で設定できる最小のスコープ・権限と、実際に制限できる単位(プロジェクト単位にできるか)を、作成前に確認する**。権限の付与は、作者が行う。

**Workers と Pages の違い(確認できた範囲)**

| | Workers の静的アセット(第一候補) | Pages(代替) |
|---|---|---|
| コマンド | `wrangler deploy` | `wrangler pages deploy` |
| 独自ドメイン | apex・サブドメインとも、有効な Cloudflare ゾーンが要る | 外部 DNS のサブドメインに CNAME を向ける経路がある。apex はゾーンが要る |
| ファイル数・サイズ | 20,000 件、1 ファイル 25 MiB([Workers の制限(静的アセット)](https://developers.cloudflare.com/workers/platform/limits/#static-assets)。Codex のレビューが確認した内容で、Claude は再取得していない) | 同じ数字(Direct Upload の資料) |
| ビルド・デプロイの回数 | Actions からのアップロードの回数制限は、**確認できていない** | Git 連携のビルドは月 500 回(Git 連携の枠。Actions のアップロードの根拠ではない) |
| プレビュー | 方式を、本番移行前に確認する(**未確認**) | プルリクエストごとに自動(Git 連携)。Direct Upload ではブランチ指定 |

**撤退の条件(代替へ)**: 規約の確認で、商用・販売の案内が、合わないと分かったとき、または、Free が終了されたとき。代替は、**Netlify Personal(月 9 USD)**。10 GB・30 万要求の仮定では、本番更新が月 49 回までなら 995 クレジットで収まる(§3.5)。**50 回・10 GB では 1,010 クレジットとなり、Personal の基本枠(1,000)を超える**。自動チャージが有効なら約 14 USD、無効なら停止しうる。余裕が小さいため、運用上の上限には余白を持たせる(例: 変更をまとめて、本番へ出す)。

## 5. 旧サイト・進捗の救済

**前提(公式)**: GitHub Free で、現行のリポジトリを private にすると、旧 Pages(`https://shn4pt.github.io/dokushu-academia/`)は、自動で停止する。**新サイトの公開の維持と、旧サイトの救済の維持は、別に設計する。**

**旧オリジンの性質**: 進捗は、オリジン `https://shn4pt.github.io` の `localStorage`(キー `llm-learning:progress`)にある。`localStorage` は、パスでなく、オリジン単位(ウェブの標準)。旧 URL のパスは、リポジトリ名と同じ(`/dokushu-academia/`)。ユーザーサイト用のリポジトリ(`shn4pt.github.io`)は、**ない**(2026-10-14、ホスト直下は 404)。

### 5.1 候補の比較

| | 候補 A: 現行の公開リポジトリを、旧サイトとして残し、開発は新しい private リポジトリへ | 候補 B: 旧オリジンに、移行専用の公開成果物を、別の公開リポジトリで置く | 候補 C: 旧側を残さない |
|---|---|---|---|
| 内容 | 現行リポジトリは公開のまま。`main` を、移行の案内(と進捗の書き出し)だけの小さなサイトに置き換える(追加のコミットで。履歴は書き換えない)。今後の開発は、新規の private リポジトリ(現行のコードと履歴を、コピーして始める) | `shn4pt.github.io` のユーザーサイト(公開)に、`/dokushu-academia/` の案内ページを置く。現行リポジトリは、private にして、旧 Pages は停止 | 案内の期間を設け、終了時の影響を示して、旧 Pages を停止 |
| 旧 URL(`/dokushu-academia/…`) | **残る**(Pages を、そのまま使う) | 残るかは、**未確認**(プロジェクトのパスが、停止した後に、ユーザーサイトの 404 や、同じパスのディレクトリが、要求を受けるか) | 停止(GitHub の 404) |
| 同じオリジンの進捗の書き出し | **可能**(同じオリジンのページから、`localStorage` を読める) | 可能(同じオリジン。ユーザーサイトが受けられれば) | **不可**(終了後は、読む手段がない) |
| 出典・ライセンス・更新記録・報告先の、4 種類の GitHub リンク | **そのまま有効**(公開リポジトリが残るので。ただし、内容は、旧リポジトリの時点で止まる) | 無効(現行リポジトリが private になるので。**移行前に、付け替えが要る**) | 無効 |
| リポジトリの移転・名前の変更 | **不要** | 不要(ただし、ユーザーサイト用リポジトリの新規作成が要る) | 不要 |
| 回収の観点 | 回収ではない(すでに公開済みの内容は、公開のまま) | 同じ | 同じ |
| リスク | 公開リポジトリに、旧コードと履歴が、残り続ける(**private 化の目的は、「今後の資産」を守ることで、回収ではない**。合意済み)。2 つのリポジトリの管理 | ユーザーサイトの 404 の挙動、プロジェクトのパスとの競合が、未確認。旧 URL が、機能しない可能性 | 旧リンクを開く人、移行を知らない人の救済が、失われる |
| 作者の合意が要る点 | 旧公開リポジトリを、公開のまま残すこと | 新しい公開リポジトリの作成 | 終了の影響を受け入れること |

**推奨: 候補 A。** 理由: ①旧 URL・同じオリジン・4 種類のリンクが、**追加の仕組みなしで、そのまま使える**。②**未確認の挙動(ユーザーサイトの 404、リポジトリ名の変更・移転の影響)に、依存しない**。③既存の公開物を、回収しないという合意と整合し、元に戻しやすい(新しい private リポジトリは、コピーなので、現行を壊さない)。**必ず、本番移行前に、検証する**(§10)。

### 5.2 移行・案内の設計(候補 A)

- **旧サイトには、案内と同じオリジンで動く、進捗のエクスポート機能そのものを残す**(導線だけにしない)。現行の `src/progress.ts` の読み込みは、例外や不正な形式のとき、空の状態を返し、エクスポートも、読み込み後の状態を出す。そのまま使うと、救済すべき進捗を、空と誤判定しうる。**読める元の進捗の文字列は、API キーを含めずに、バックアップできるようにする**。
- **自動転送は、「保存なし」または「既知の正常な形式で、学習記録がない」と確定したときだけ**。**読み取りの失敗(ストレージの拒否)、JSON の破損、未知の version のときは、自動転送も、保存値の上書きもしない**。手動の移動と、復旧の案内を出す。
- **進捗があるとき**: 自動で転送せず、案内を先に出す(新サイトの URL、進捗を書き出す方法、新サイトで「インポート」する方法、自己診断の回答と API の設定は、引き継がれないこと)。
- 検証する場合: 旧ハッシュ付き URL、空の進捗、正常な全記録(completed / quiz / questions / reading / lastVisited)、破損、未知の version、ストレージの拒否。
- 保存データがない場合は、新 URL へ転送してよい。旧ハッシュ URL(`#/lesson/pm-1` など)は、**案内を出した後**に、新しい URL の、対応するパスへ誘導する。
- **API キーを、移行用のファイルや分析へ含めない**(現行のエクスポートの仕様のとおり。進捗に、キーは含まれない)。
- 旧サイトの案内期間: 新サイトの公開と、移行後の確認(§7)の後、**期間で切らない**(PM の方針。plan.md §4.6)。終了は、別途、作者が決める。
- **旧サイトは、新サイトの正規 URL を、指す**(案内ページの `canonical` ではなく、本文のリンクで案内。正規 URL の扱いは、検索エンジンへの影響があるので、**試作で検証する**)。サーバー側の 301 は、GitHub Pages ではできない(確認した範囲。**未確認**の可能性を残す)ので、JS の転送と案内が、代わりになる。評価の引き継ぎは、保証しない。
- **Search Console の「アドレス変更」**: 公式資料では、ドメインまたはサブドメインの移転に使い、**移転・転送の後**に使う。`shn4pt.github.io` の**プロジェクト配下(パス)**から、独自ドメインへの移転に使えるかは、資料に明記がなく、**未確認**。GitHub Pages では、301 ができないので、前提(転送の後に使う)が、満たせない可能性がある。使えない場合は、サイトマップの送信、新サイトの正規 URL、案内で、時間をかけて、移るのを待つ。**効果は、保証しない**。

## 7. 移行・切り戻しのチェックリスト

**候補 A の本線の順番**: 新しい private リポジトリの作成と、CI・権限の準備(作者の作業) → 別 URL(プレビュー)での検証 → 新サイトと旧サイトの案内の切り替え。現行の公開リポジトリは、private にしない。下の手順 3〜8 は、この順で読む。手順 9 と「private 化の後」は、現行リポジトリを private にする候補 B・C を選んだ場合の、別の項目。

**private 化の前**(新サイトの公開維持と、旧サイトの救済を、両方満たす):
1. 作者の判断: 継続費用の上限、配信先、公開範囲、移行の時期(§9)。候補 A では、**新しい private リポジトリの作成と、CI・権限の準備**もここで行う(作者の作業)。
2. 配信先の規約の確認(§11 の質問案)。**カード情報の処理・収集の禁止(Cloudflare 2.2.1(h))、Free の終了(2.6)を含む**。
3. 新サイトを、**本番とは別の URL(プレビュー)**で公開し、PR #17 の検証(`docs/seo/prototype.md`)を、その配信先で繰り返す: HTTP の取得(本文・出典・内部リンク・固有のメタ情報)、404 のステータス(`404.html`)、スラッシュの転送、HTTP ヘッダーの CSP、`robots`、サイトマップ、旧ハッシュ URL の転送、進捗の保護。**プレビューが、検索に出ない設定になっているか**も確認する。
4. ライセンス文書の公開ページ、更新記録、報告先の、**新サイトでの置き換え**(§6)。
5. 旧サイト(候補 A)に、移行の案内と、**同じオリジンで動くエクスポート機能そのもの**を載せる。**保存済みの進捗があるとき、また、読み取りの失敗・破損・未知の形式のとき、自動で転送しない**ことを、テスト用のプロファイルで確認する(§5.2 の検証項目)。ライセンス文書など、4 種類のリンクの先を、旧 `main` から消さない。
6. 本番の切り替え: 新サイトを公開(独自ドメインを使うなら、DNS)。**旧 URL は、残す**。

9. **ここで初めて、private 化を判断する**。実施前に、**独自ドメインを、GitHub Pages に向けた設定があれば、その設定と、GitHub Pages を指す DNS の記録だけを、先に外すか更新する**(公式資料。GitHub 側に、使わない向き先を残さない)。**新しい配信先を指す DNS は、外さない**。候補 A では、現行リポジトリを private にしないので、この手順は、**新しい private リポジトリを作って、そちらで開発する**形になる。
**private 化の後(候補 B・C を選んだ場合)**: 旧 Pages は、すでに停止している。切り戻しは、可視性を public に戻すか、旧サイトを別の公開リポジトリで再現する。**可視性を戻したとき、Pages が自動で再公開されるかは、公式資料で確認できていない(未確認。試さない)**。
