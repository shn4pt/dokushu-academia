# 公開文書の設計: 新しい private ソースから配信しても、出典・利用条件・更新記録・報告先を公開して読める(Issue #24)

文書設計と、ローカル専用の画面案までの記録。**この PR では、本番のルート・リンク・教材・出典・確認日・ライセンス自体を変更しない。** private の GitHub には、アクセスしていない(現行の公開リポジトリのファイルだけを読んだ)。外部公開、全教材への展開、アカウント作成、契約、購入、DNS、権限付与、private 化、リポジトリ移転、第三者への送信は、していない。**法的な適合は、確認していない**(専門家の確認でも、権利の保証でもない)。

## 0. 要約

- 現在、公開読者がリポジトリ(github.com/shn4pt/dokushu-academia)へ出るリンクは **4 種類**(§2)。新しい開発リポジトリが private になると、**そのうち、コミットへのリンクは、公開読者にはリンク切れになる**。ほかの 3 つは、旧公開リポジトリを残す候補 A(`hosting.md` §5)では、リンクとしては残るが、**内容は、分岐した時点で止まる**(新しい開発の変更が、反映されない)。
- 設計の柱(§3〜§6): ①ライセンス・資料の扱い・出典・更新記録を、**新サイトの中の公開ページ**(静的な HTML)にする。②内容の唯一の元は、**リポジトリの元ファイル**(`LICENSE-CONTENT.md`・`docs/licenses.md`・`LICENSE`・出典の記録)で、ビルド時に生成し、転記しない。③**公開の更新記録は、人が書いた記録(`changes`)だけ**にして、コミットへのリンク・コミットの題名は出さない。④誤りの報告先は、当面、**旧公開リポジトリの Issues を継続**し、作者が確認する(第一案)。
- **設計で見つかった問題(§2.3)**: `LICENSE-CONTENT.md` に、**旧サイトの URL が、表示の指定として、書かれている**(独習アカデミアの帰属表示の URL)。新しい URL に移るとき、作者の判断が要る。`docs/licenses.md` には、**公開に向かない内部の記述**(「残っている確認(作者の判断が要る点)」、エージェントによる確認の経過)があり、**そのまま公開ページにしない**(公開する範囲の指定が要る)。
- 画面案は、ローカル専用(`npm run build:public-docs-mock`)。1000px と 390px で確認した(§9)。

1. **帰属表示の URL が、旧サイトの URL で固定されている。** `LICENSE-CONTENT.md` の「表示」の説明と「表示の例」に、`https://shn4pt.github.io/dokushu-academia/` がある。独自ドメインへ移ったとき、(a)旧 URL のまま(候補 A では、旧サイトは、案内として残る)、(b)新しい URL に変える、のどちらにするか。**ライセンスの文面は、変更していない**(この PR の範囲外)。変更する場合も、すでに公開した文章への影響(旧 URL を帰属として使っている再利用者)を、作者が判断する。
2. **`docs/licenses.md` は、内部の運用の記録を含む。** 「残っている確認(作者の判断が要る点)」の節には、エージェントによる確認の経過、レッスンごとの書き直しの詳細などがある。**公開ページに、そのまま出さない**。公開する範囲(方針・一覧)と、しない範囲(運用メモ)を、元ファイルの中で、指定する必要がある(§4.1)。

4. **「このサイトは、広告も課金もない(2026-10-12 時点)」** の記述が、`docs/licenses.md` にある。**収益化を始めるとき、この文は、事実と合わなくなり、NC の資料を含むレッスンの扱いも、見直しが要る**(§7)。公開ページに出す場合は、日付つきの記述であることを、保つ。

## 4. 元ファイルを唯一の内容源にする方法

### 4.1 生成と範囲の指定
- ライセンス・資料の扱いのページは、**元ファイルを、ビルド時に、HTML へ変換して作る**。ページに、元ファイルのパスと内容の SHA-256 を示す(画面案で実装済み)。転記・手でのコピーはしない。
- `docs/licenses.md` は、公開する範囲を、**元ファイルの中の印**(例: HTML コメントの `public:start` / `public:end`)で指定する案を第一案にする。印がない範囲(運用メモ)は、公開しない。別ファイルへ分ける案は、**内容が 2 か所に分かれ、ずれる**ので、採らない。
- 公開版の生成で、リポジトリ内のパス(`src/...`)への言及は、そのまま出る。公開の読者には、意味が薄いので、文面を、公開向けに直すかは、作者の判断(§11)。**元の文章は、この PR で変更していない**。

### 4.2 ずれと、偽の確認日の防止
- **ライセンス文書の転記ずれ**: 生成物に、元ファイルの SHA-256 を埋め込み、CI で、元ファイルから再生成した値と照合する(画面案のテストで、同じ検査をしている)。
- **資料の一覧の表**: 出典の記録(`lesson-sources.json`)から、資料名・ライセンス・使っているレッスンを、スクリプトで再計算し、`docs/licenses.md` の表と照合する(不一致は、ビルドを失敗させる)案。**作成は、後続の実装**。
- **偽の確認日の更新**: 公開ページに出る確認日は、`lesson-sources.json` の `checkedAt` だけを使う。**`checkedAt` が、基準のブランチと比べて変わった変更には、同じ日付の `changes` の記録がある**ことを、CI で要求する案(出典の記録の検査 `check-sources` の拡張)。公開ページの生成で、確認日を、自動で補完・更新しない。
- 人が書いた更新記録(`changes`)に、「確認日は据え置き」のように、確認していないことを書く運用は、現在のとおり維持する。

### 4.3 更新記録: コミットのリンクと題名を出さない
- **公開の更新記録は、`lesson-sources.json` の `changes`(人が書いた記録)と、作成日だけ**にする。画面案で、PM-1 を例に示した(`docs/seo/public-docs/lesson-note-*.png`)。
- **コミットへのリンク・題名は、公開しない。** 理由: ①新しい開発リポジトリが private なら、リンクは、公開の読者に、リンク切れになる。②コミットの題名は、開発の経過(レビューの対応、Issue 番号など)を含み、公開の記録としては、不適切になりうる。③`lesson-history.json` は、現在、アプリの JavaScript に含まれる。**公開用のビルドでは、コミットの一覧を、含めない**(作成日だけを、別の小さなデータにする)。
- 分岐前の(公開済みの)コミットへのリンクを、残したい場合は、**分岐の時点のコミット**を記録し、それ以前のものだけにリンクする案がある。**実利が小さく、リンク切れのリスクがあるので、第一案にはしない。**
- **すでに公開されている旧リポジトリの履歴は、回収しない**(合意済み)。公開のままの履歴は、旧公開リポジトリで、読める。

## 5. 旧公開リポジトリを残す候補 A との整合

- 旧公開リポジトリには、`LICENSE`・`LICENSE-CONTENT.md`・`docs/licenses.md`・履歴・Issues が残る。**旧 `main` から、これらを消さない**(`hosting.md` §7 の条件)。
- 旧 `main` の文書は、分岐の時点で止まる。**新サイトの `/licenses/` が、現行の正**(新しい開発の側の元ファイルから生成)。旧リポジトリの文書が、古くなることを、新サイトの案内に書く(例: 「最新の内容は、このサイトの『ライセンス』を参照」)。**この文言は、後続の作業で決める**。
- 旧リポジトリの履歴(コミットのページ)は、公開のままなので、旧サイトのレッスンの更新記録のリンクは、有効なまま。
- **旧リポジトリをアーカイブすると、Issues が読み取り専用になり、報告先として使えなくなる**。第一案(§6)を採る間は、アーカイブしない(要確認: GitHub の公式資料での確認は、この PR では、していない)。
- 新しい private リポジトリの**コミットの URL は、公開の読者に出さない**(§4.3)。

## 6. 公開の報告先(第一案: 旧公開 Issues を継続)

**第一案**: 当面、**旧公開リポジトリの Issues** を、公開の報告先にする。作者が確認し、開発リポジトリ(private)の側で対応する。新しい問い合わせのサービスやアカウントは、前提にしない。氏名・メールアドレスなどの、**実在の連絡先は、創作しない**。

**運用の定義**:
1. **受け付け**: 新サイトの `/report/` で、旧公開 Issues(`.../issues/new`)へ案内する。報告に、レッスンの番号、ページの URL、誤りだと思う箇所(短い引用)、根拠(資料の URL)を書いてもらう。**公開の場所であること、個人情報・API キー・非公開の情報を書かないこと**を、明示する(画面案)。
2. **確認**: 作者が、確認する。**頻度は、作者の判断**(運営は、週 3〜5 時間の制約の中。即時の対応は約束しない、と書く)。
3. **対応**: 確認して、必要なら、新しい開発の側で、教材を直す。**公開の Issue に、確認の結果をコメントする**。非公開の側の Issue・コミットの URL は、書かない。
4. **記録**: 直したときは、レッスン末尾の更新記録(`changes`)に、人が書いて残す。確認日は、出典を読み直したときだけ更新する。
5. **届く保証**: 作者が、公開 Issues の通知を受け取れること(GitHub の通知の設定)は、**作者側の前提**。通知が届かなくなると、報告が埋もれる。

**限界・未決**: ①報告に、**GitHub のアカウントが要る**(敷居が高い)。アカウントを持たない人のための方法は、**まだ決まっていない**(決めるのは作者。メールなどの、実在の連絡先を使う場合は、作者の判断)。②公開 Issues への**スパムや、悪意のある投稿**への対応。③旧リポジトリの名前や所有者を変えると、リンクが変わりうる(リポジトリの移転は、この Issue の対象外)。

## 7. ライセンス方針の維持(MIT / CC BY-SA と、原典由来の例外)

- **維持**: コード MIT、文章 CC BY-SA 4.0、**資料から訳した部分は、原典の条件が優先**(BY-SA、BY-NC-SA、BY-NC-ND、BY など)。公開ページは、この方針を、元ファイルのとおりに示す。**方針を、この PR で変更しない**。
- **NC(非営利)の資料を含むレッスンがある**: CC BY-NC-SA の資料(OpenStax の教科書、Pro Git など)を訳したレッスンは、**非営利の目的に限る**(`docs/licenses.md`)。`docs/licenses.md` の一覧から、該当するレッスンは、ac-1〜6・ma-1〜6・mg-3・pl-3・pl-4・pl-6・sg-1・sg-2・sg-5・sg-6・sw-2(Pro Git の部分)など。
- **将来、有料商品を出すときの注意**: **無料の教材と有料の商品を、分けただけでは、NC の条件が解決したとは言えない。** 有料商品が、NC の資料を訳した部分を含まないこと、無料の教材に、広告・課金・商用の誘導(商用の文脈での利用になりうる)がないかの確認が、別に要る。**この文書は、その適合を、確認していない**(法的な判断は、専門家の確認が必要になりうる)。収益化を始める前に、`docs/licenses.md` の方針どおり、NC のレッスンを見直す。
- 資料の利用条件の「確認」は、AI(Claude)と、Codex のレビューによるもので、**専門家の確認ではない**。

## 8. 初期 HTML と、SPA での閲覧

- `/licenses/`・`/licenses/materials/`・`/report/` は、**静的な HTML(ビルド時に生成)**にする。JavaScript がなくても、本文・リンクが読める。検索エンジンと、AI のクローラーに、本文が見える。これらは、公開する価値のある内容(ライセンス・利用条件)なので、noindex にしない(**索引へ出すかは、作者の判断**。出さなくても、機能する)。
- レッスン末尾の「出典と更新記録」は、`<details>` の中身が、**初期の HTML にある**(JavaScript なしでも、開くと読める)。更新記録は、公開の記録(`changes`)だけ。
- `/sources/` の一覧(172 件)は、現在は、ブラウザで描画されている。初期の HTML に含める作業は、**全展開の設計**(`docs/seo/rollout.md`、Issue #25)で扱う。
- SPA の中の移動でも、同じ URL(末尾スラッシュ付き)にする。メタ情報(タイトル・説明・canonical)は、既存の仕組み(`seo.ts`)を、これらのページに追加する(実装は後続)。
- **ベース(`/dokushu-academia/` か `/`)に依存しない**: 内部リンクは、共通部品に任せる。

## 10. 公開前チェック(実装・公開の前に、満たすこと)

1. `/licenses/`・`/licenses/materials/`・`/report/` が、新サイトの URL で、HTML として読める(JavaScript なしを含む)。
2. フッター・レッスン末尾・出典ページの、リポジトリへのリンクが、**サイト内のページ**に替わっている。コミットへのリンクと題名が、公開の配布物(HTML・JavaScript)に含まれない。
3. 元ファイルの SHA-256 が、CI で照合されている。資料の一覧の表が、出典の記録と照合されている。`checkedAt` の変更に、対応する `changes` がある。
4. `docs/licenses.md` の公開する範囲が指定され、運用メモが、公開ページに出ない。
5. 旧公開リポジトリの `main` に、`LICENSE`・`LICENSE-CONTENT.md`・`docs/licenses.md` が残っている。Issues が有効で、アーカイブされていない。
6. 報告先: 作者が、公開 Issues の通知を受け取れる。確認の頻度が決まっている。
7. 帰属表示の URL(§2.3 の 1)の扱いが、決まっている。
8. 旧サイトの案内(`legacy-rescue.md`)と、新サイトの `/licenses/` の、整合を確認した。

## 11. 残る作者判断

1. **帰属表示の URL**: 旧 URL のまま残すか、新しい URL に替えるか(§2.3 の 1)。
2. **公開する範囲**: `docs/licenses.md` の、公開する範囲と、公開向けの文面(リポジトリ内のパスへの言及の扱い)。
3. **報告先**: 旧公開 Issues の継続(第一案)でよいか。確認の頻度。アカウントを持たない人のための方法(実在の連絡先は、作者が決める)。
4. **索引へ出すか**: ライセンス・利用条件のページを、検索に出すか。
5. **収益化の前の見直し**: NC の資料を含むレッスンの扱い(§7)。
