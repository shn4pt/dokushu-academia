## 0. 要約

- **範囲**: 生成する公開ページは、**約 280 ページ**(講座一覧・地図・ロードマップ・講座 20・段階 73・レッスン 172・用語集・出典・公開文書 3、ほか)。個人ページ(進捗・復習・API キー・検索)は、殻(noindex)のまま。未生成の有効な教材が 404 になる試作の制限は、**生成の一覧を、既存のデータから作る**ことで、本番の前に解消する(SPA の fallback で 200 にして隠さない)。
- **検証**: 172 レッスン × 検証項目の**行列**(§3)。**7 件+対照の診断が通ったことは、全教材の成功と扱わない**。全件の診断は、実装の後の、最初の段階(ローカル全教材検証)で行う。
- **費用(推定)**: 生成のビルド時間は、ローカルで +数秒〜十数秒の見込み。**CI の分数が、本当の制約**: 実測では、現在の CI が、1 回 約 6.5 分(387 秒)(1 ジョブ)。デプロイが、約 8 分(3 ジョブの切り上げ)。**現在の開発のペース(2026-10-13〜15)のままだと、GitHub Free の private の月 2,000 分を、約 11 日で超える見込み**(§4.4。1 日あたり CI 約 17 回 × 7 分 + デプロイ約 7 回 × 8 分 = 175 分/日 → 2,000 ÷ 175 ≒ 11.4 日)。private 化の前に、CI の回し方の見直しが要る。
- **段階**: ①ローカル全教材検証 → ②外部プレビュー → ③独自ドメインの本番 → ④開発リポジトリの移行。**前段の完了だけで、後段を自動実行しない**。各段階に、Go/No-Go と、作者の判断(§7)を置く。
- **本番の前提(完了が必要)**: 旧進捗の救済(#23 / PR #26)と、公開文書(#24 / PR #27)。**この 2 つは、まだ、レビュー中で、採用されていない。**

### 未生成の有効な教材が 404 になる制限の解消方針
- **現在の制限**: 試作は、3 ページだけを生成する。ほかの有効な URL(例: `/lesson/pm-2/`)は、配信側の 404(の殻)から、ブラウザで描画され、**HTTP の状態が 404 になる**。
- **方針**: ①生成するページの一覧を、**手書きのリストではなく、データから作る**(`catalog.courses`・`curriculum.stages`・`isReady` なレッスン)。②**ビルドの検査**: 「公開扱いのレッスンの ID すべてに、生成した HTML がある」「sitemap の URL すべてに、生成物がある」「生成物のすべてが、データに存在する」。③**直接アクセスの検査**: 有効な URL は 200 で本文あり、無効な URL は 404。④SPA の fallback で、未知の URL を 200 にして隠さない。
- **ホストごとの注意**: Cloudflare は、`404.html` がないと、SPA として、ルートを 200 で返す(`hosting.md` §3.3)。`404.html` を、必ず置く。

### 3.4 実行の設計(実施は、実装の後)

| prerender(約 280 ページ) | 1〜10 秒 | 2〜20 秒 | [既存の記録]172 本文で 1.0 秒 + 枠の描画 + 起動 0.4 秒。[実測]ページ追加の影響は小さい。最悪を 10 秒と置く |

### 4.3 テストの時間(推定)

[実測]CI では、全体 1,018 件(1,015 成功・3 スキップ)が 319 秒(平均 0.31 秒/件、ワーカー 2。run 38667805700)。
- **全 172 レッスンの引き継ぎ診断**: 172 × 2(進捗なし・あり)= 344 件(本番相当のビルド)+ 344 件(開発用ビルド)= 688 件 → 688 × 0.2〜0.4 秒 = **約 2.3〜4.6 分**(CI)。
- **HTTP の検査(A1・A2・A6a・A7)**: 172 × 数 ミリ秒〜 0.1 秒 → **0.5 分未満**(推定)。
- **型ごとの操作**: 約 70〜100 件 × 0.3 秒 = **約 0.5 分**。
- **合計**: 全展開の完全な検証は、CI で **約 4〜7 分**(推定)。**内訳と余裕**: 診断 688 件の 2.3〜4.6 分 + HTTP の検査 0.5 分 + 型ごとの操作 0.5 分 = 3.3〜5.6 分。これに、ブラウザの起動・待ち・失敗時の再実行(CI は、失敗した件を 1 回やり直す設定)などの余裕として、**約 20〜25% を足して 4〜7 分**とした(**余裕の割合は、仮定**)。**現在の検査との重複**: 現在の診断(8 レッスン・16 件×2 ビルド。約 11 + 数秒)は、688 件に含まれるので、現在の 6.5 分から、**この分(約 0.3 分)を引く余地がある**が、小さいので、引かない(保守的に、そのまま足す)。**そのまま足すと、1 回あたり 約 10〜13 分**になる。

### 4.4 CI の分数の試算(GitHub Free の private リポジトリ)

**前提**: `hosting.md` §3.2 のとおり、private リポジトリでは、Free で**月 2,000 分**(Linux、公開リポジトリは無料)。ジョブごとに、分へ切り上げる。以下は、**推定の式と仮定**で、請求の保証ではない。

- **GitHub Free の枠は、このリポジトリ専用ではなく、所有者のアカウントの枠**(ほかの private リポジトリの実行も、同じ枠を使う)。**再実行・失敗・取り消しの実行**、artifact の保管などは、別の余裕が要る(**artifact の保管などの上限は、GitHub の公式資料で、別枠として示されている。この文書では、数値を確認していない**)。GitHub Pages(標準のランナー)の実行には、無料の例外の記載がある(公式資料)が、**将来の Cloudflare 向けの Actions には、当てはまらない**。**現在の Pages のデプロイの実時間を、Cloudflare 向けの仮定に使う場合は、同一の請求実績ではない**。
- **月の分数 = PR の CI 回数 × 1 回の分数 + main へのデプロイ回数 × 1 回の分数**
- **1 回の分数**(実績ベース): PR の CI = 7 分(387 秒を切り上げ)。デプロイ = 8 分(`test` 6 + `build` 1 + `deploy` 1)。
- **全展開後に、現在の CI の組み立てのまま、完全な検証を足した場合**: PR の CI = 約 12〜14 分、デプロイ = 約 14〜16 分(`test` ジョブにも含まれるため)。

| ケース | 前提(回数/月) | 現在の CI の組み立て | 全展開 + 完全な検証を、毎回 |
|---|---|---|---|
| 運営の平常(**仮定**。週 3〜5 時間で、まとめて公開) | PR 8、デプロイ 8 | 8×7 + 8×8 = **120 分** | 8×13 + 8×15 = **224 分** |
| 中間(**仮定**) | PR 30、デプロイ 20 | 30×7 + 20×8 = **370 分** | 30×13 + 20×15 = **690 分** |
| 2026-10-13〜15 の実績の延長(**実測の回数**。CI 約 17 回/日、デプロイ約 7 回/日) | PR 約 500、デプロイ約 220 | 500×7 + 220×8 = **約 5,260 分**(**2,000 分を超える**。約 11 日で到達) | 500×13 + 220×15 = 約 9,800 分 |

**読み方**:
- **平常の運営のペースなら、現在の組み立てでも、全展開 + 完全な検証を毎回回しても、2,000 分に収まる見込み**(推定)。
- **ただし、開発が集中する期間のペース(実測)のままだと、private 化後は、短期間で上限に達する。** private 化の前に、**CI の回し方を見直す**(§4.5)。
- **公開リポジトリのままなら、課金はない**(現在)。private 化(段階④)が、制約を生む。

### 4.5 CI の分数を抑える案(実装は後続・作者の判断)
1. **完全な検証(全 172 の診断)は、PR の毎回でなく、手動の実行(`workflow_dispatch`)、または、main への変更のうち、教材・生成の変更があるときだけ**にする。PR の毎回は、現在と同じ軽い検査(代表 8 レッスン + 対照)にする。
2. **デプロイ時に、CI を二重に回さない**(PR で通ったものを、main で再度、全体を回している。`deploy.yml` が、`ci.yml` を呼び出す)。main では、ビルドと配信の確認だけにする案。**公開の安全の水準が下がるので、作者の判断**。
3. **文書だけの変更で、ビルド・テストを回さない**(`paths-ignore`)。**必須チェックの設定との兼ね合いが要る**。
4. 同じ PR の古い実行の取り消し(`concurrency`)。
5. プレイライトの導入キャッシュ、`npm ci` のキャッシュ(現在、`setup-node` の `cache: npm` あり)。
6. **GitHub のプランの変更(有料のプラン)は、費用が増える**。今回は、検討しない。

### 5.3 外部プレビューで確認する項目(段階②。実ホスティングの別 URL)
`hosting.md` §8 の手順に沿う。**本番とは別の URL。noindex を設定する。**
1. **noindex の設定の確認(索引にないことの確認ではない)**: 全対象のレスポンスに、`X-Robots-Tag: noindex`(または、`<meta name="robots" content="noindex">`)が付いていることを、**実際に HTTP で取得して確かめる**(推測で、設定済みとしない)。**`robots.txt` で、プレビューのクロールを拒否しない**: クロール拒否があると、クローラーが noindex を読めない([Google の公式の説明](https://developers.google.com/search/docs/crawling-indexing/block-indexing))。**ヘッダーを読むだけでは、「検索に出ていない」ことは確認できない**。実際の索引の状態は、**別に確認する(未確認)**。Search Console には、登録しない(この文書では実行しない)。**非公開であることが必要なプレビューは、noindex ではなく、アクセス制限(認証など)を、別の候補として検討する**(noindex は、秘密を守る機能ではない)。
2. HTTP の挙動: 有効な URL が 200、無効が 404(`404.html`)。スラッシュなしの転送のステータス(307/308/301)。CSP などのヘッダー。
3. 全アセットの解決、キャッシュのヘッダー、圧縮(gzip / brotli)。
4. 旧ハッシュ URL の転送(`legacy-redirect.js`)、進捗の保護、別オリジンの進捗の書き出し・読み込み(#23 の仕組み)。
5. 実際のファイル数・サイズが、上限(20,000 件、1 ファイル 25 MiB)以内。
6. API トークンの権限(最小)。デプロイの方式(Actions からのアップロード)。ここで、**作者のアカウントの作成と権限の付与が、必要になる**。

## 6. 修正が必要な教材が出た場合の扱い

## 8. 切り戻し条件(実施時)

**共通の原則**: 切り戻しの手順を、**実施の前に、実際に試す**(`hosting.md` §7 の項目 8)。**旧サイトと進捗の救済は、新サイトが安定するまで、消さない**。履歴の書き換え・削除は、しない。

| 対象 | 切り戻しの条件(いずれか) | 手順 |
|---|---|---|
| **新サイトの配信** | 本番の挙動が、プレビューの検証と食い違う(404 の状態、ヘッダー、リンク切れ)。検索・読者の導線が、壊れた。費用・規約の問題が、判明した | **初回公開**(前のデプロイがない): **公開の前に、検証済みの退避の成果物を、保管しておく**(旧アプリの配信物、または、プレビューで確認済みの成果物)。切り戻しは、**既知の正常な配信先**(旧サイトの配信、または、退避の成果物)へ向ける。**2 回目以降**: 配信先の前のデプロイに戻す(Git の `revert` で、再ビルド・再アップロード)。**旧サイトは、動いたまま**だが、**候補 A の旧サイトは、案内ページになり、空データの読者を、新サイトへ自動転送する**。**新サイトの障害時に、旧側から、障害のある新側へ送り直さない**ため、**先に、運営者向けの転送停止の設定を使う**(次の行) |
| **旧サイトと進捗の救済** | 案内ページが、進捗を失わせる(誤った自動転送、保存データの上書き)。書き出し・読み込みの往復が、本番で失敗する | **運営者向けの転送停止の設定で、自動転送を一括で無効にする**(`legacy-rescue.md`: ビルド時の `AUTO_FORWARD=off`。利用者の「止める」ボタンとは別。**この設定は、本番の前に、実装・検証しておく**。試作では、ローカルで検証済み)。旧サイトの案内を、前の版に戻す。**案内から、旧アプリを復元したときも、書き出しが使える**ようにしておく(旧アプリの配信物を、保管する)。**元の保存データには、触らない** |
| **DNS** | 独自ドメインの名前解決・HTTPS が、不安定。誤った向き先 | DNS を、**既知の正常な配信先**へ向ける(**変更前の設定を、必ず記録しておく**)。**新規のドメインで、変更前が未設定の場合は、「戻す」だけでは、読者が読めない**。復旧先として、**既知の正常な配信先**(旧サイトのホスト、または、検証済みの退避の成果物の配信先)を、**あらかじめ指定しておく**。TTL の影響で、反映に時間がかかることを、織り込む |
| **公開リンク** | 外部のリンク(旧 URL、出典・ライセンスのリンク)が、404 になる。`/licenses/`・`/report/` が、開けない | 旧 URL は、**残す**(候補 A)。公開文書のリンクを、前の(旧リポジトリの)リンクに戻す |
| **検索** | 重複した URL・誤った canonical による、検索の混乱 | canonical・sitemap を、直す。新旧の同時公開の期間の、重複を避ける。**Search Console のアドレス変更は、転送の後に行う前提**で、使えるかは未確認(`hosting.md` §5.2) |
| **開発リポジトリの移行(段階④)** | CI の分数が、上限を超える。公開文書・報告先が、機能しない | **配信の復旧と、開発の復旧を、分ける**。①**配信**: 既知の安全な、**公開済みの成果物**へ戻す(新旧の公開成果物を、保管しておく)。②**開発**: 旧公開リポジトリでの開発に戻れるのは、**分岐前の履歴の範囲**だけ。**private 側の新しい履歴を、丸ごと公開リポジトリへ push しない**(将来の非公開のソース・運営情報を、再公開する経路になる)。戻す必要があるときは、**公開してよいことを確認した変更だけを、選んで**移す。③**CI の枠を超えたとき**も、private の資産を公開しない代替(ローカルで、ビルドして、成果物だけを、手動で配信する。または、実行を止める)で対応する。private 化は、**判断を急がない** |

**切り戻しの判断は、作者**。DNS・公開・リポジトリの設定の変更は、作者の権限で行う(Claude は、設定を実行しない)。
