# 講座づくりの手順書

独習アカデミアの講座とレッスンを、毎回同じ品質で作るための手順。方針は `docs/concept.md`、運営の制約は次のとおり(2026-10-09)。
- 運営に使える時間は週 3〜5 時間。追加の費用は月数千円まで。
- 公開前に、本人が必ず確認するのは、**高リスクの分野(根拠の種類が「法令・基準」の講座)と、方針(講座の構成・優先度)だけ**。
- 公開は、講座単位(基礎・実践・応用の段階ごと)でまとめて行う。

この手順は、Claude Code のスキル(`.claude/skills/make-lesson`・`verify-lesson`・`recheck-sources`)にもなっている。

## 守ること(正直さの原則)
1. **読んでいない資料を、読んだと書かない。** `how: read` は、原文(本文)を実際に読んだ場合だけ。要旨だけ、検索結果だけ、のときは、`search` や `partial` にして、記録の `note` に、読んだ範囲を書く。
2. **本文の数字・引用は、読んだ範囲のものだけ使う。** 要旨だけ読んだ論文なら、要旨にある数字だけを使い、そう書く。
3. **独自の整理は、そう明記する。** このサービスの枠組み、他分野への移し替え、助言は、「このサービス独自の整理」とレッスンの中にも書く。文献の主張と区別する。
4. **取得できなかった資料は、取得できなかったと記録する。** 遮断(reCAPTCHA など)や有料の壁で読めなければ、別の公開経路(公式の写し、書誌の API)を探す。それも読めなければ、使わない。第三者が公開する写しで読んだ場合は、`note` にそう書く。
5. **確認日(`checkedAt`)は、実際に確認した日だけ。** 再確認していないのに更新しない。
6. **断定できない解釈は、断定しない。** 「言えること」と「言えないこと」を分けて書く(例: 再現されなかったことの解釈)。
7. **法令・基準の講座は、「全体像と考え方」に限る。** 個別の事案は扱わない。条文と、確認した日と、改正の有無を示し、専門家に確認する線引きを書く。

## 工程
| 工程 | 内容 | 誰が |
|---|---|---|
| 0. 設計 | 講座の目的、前提、段階ごとの範囲、レッスンの問い、根拠の基準を決める。`src/data/catalog.ts` の講座のデータ(`why`・`needs`・`tiers`)と、執筆の優先度(`writingPlan`)を更新する | AI が案、**本人が承認** |
| 1. 調査 | 一次情報を取得して読む。読んだ範囲と、読めなかった事実を、メモする | AI |
| 2. 執筆 | レッスンを書く。判定問題・クイズ・出典の記録・用語集を、一緒に書く | AI |
| 3. 別の目の確認 | **執筆とは別のエージェント**が、本文の主張を、出典と突き合わせる(`verify-lesson`)。結果は `docs/verify/<ID>.md` に残す | AI(別の文脈) |
| 4. 自動検査 | 型、ビルド(出典の検査)、全テスト(ゲートを含む)、まっさらな環境でのビルド | 機械 |
| 5. 確認の材料 | `npm run review -- <講座> --checks` で、判定の要約・出典・限界の目印・別の目の確認の結果・検査の結果を、1つにまとめる | 機械(AI が実行して報告) |
| 6. 人の確認 | 高リスクの分野と方針は、本人が確認する。それ以外は、5 の材料で判断する | **本人** |
| 7. 公開 | コミット → 変更履歴の生成(`npm run history`)→ push → CI とデプロイの確認 | AI(本人の承認後) |

## 新しいレッスンを足すときの置き場所
- 本文: **Markdown**(`src/content/<ID>.md`、`loaders` に `md('<ID>')` と登録)を基本にする。専用の対話的な部品などが要るときだけ TSX(`src/lessons/<Name>.tsx`)。書き方は `docs/lesson-format.md`。
- ステージ(講座の中のまとまり): `src/data/curriculum.ts` の `stages`。LLM 以外の講座のステージには `course` を付ける。
- 講座: `src/data/catalog.ts` の `courses` の `tiers`(`stageIds` に入れる。`planned` からは外す)。
- 出典: `src/data/lesson-sources.json`(状況、確認日、出典、`note`)。ない状態でビルドは通らない。
- 用語: `src/data/glossary.ts`。
- テスト: `e2e/`。レッスンは、表示・出典・判定問題の答え合わせ・スマホの表示(`e2e/mobile.mobile.spec.ts` は自動で全レッスンを対象にする)を確かめる。
- 変更履歴: コミットしてから `npm run history`(レッスンの作成日と変更の記録。CI では生成しない)。

## 品質ゲート(自動)
- `npm run build`: 型、検索索引、出典の検査(記録がない・`verified` なのに原文の出典がない、などで失敗)。
- `npx playwright test`: 全レッスンの表示、クイズ、出典、スマホ(横スクロール・44px)、講座データの整合、**法令・基準のゲート**(`e2e/gates.spec.ts`)。
  - 法令・基準の講座のレッスンは、原典で確認済み(`verified`)で、原文を読んだ出典があり、確認日が **90 日以内**でないと、テストが失敗し、公開できない。確認日が古くなると、デプロイが止まる(再確認するまで、その講座を含む更新も公開できない)。
  - 法令・基準のレッスンの本文に、「全体像と考え方」「専門家」「確認した日」が含まれることも、確かめる。
- 出典の検査(ビルドの一部)は、`how: read` なのに「要旨のみ」「未読」などと書かれた出典を、エラーにする(要旨だけの資料を、原文を読んだことにしない)。
- 公開の前に、まっさらな環境でのビルドを確認する(手元に残った生成物で通っていないか)。`npm run review -- <講座> --checks` が、これも実行する。

## 鮮度の維持
- 月に1回、GitHub Actions(`.github/workflows/freshness.yml`、無料)が、確認日の古いレッスンと、切れた外部リンクを調べ、問題があれば issue にする。AI は使わない。
- 古さの基準(`src/data/gates.ts` の `maxAgeDays`): 法令・基準 90 日、技術・実証 180 日、学術・実務 365 日。
- 手元でも、`npm run freshness`(確認日)と `npm run freshness:links`(リンクも)で、いつでも調べられる。`npm run sources:report` は、確認日の古い順の作業リスト。
- 実際の再確認は、必要なときに Claude Code で行う(`recheck-sources`)。

## 確認の材料(工程 5)
講座(または段階)ごとに、確認の材料を、**自動で**1つの Markdown にまとめる。

```bash
npm run review -- <講座の id> [--tier basic|practice|advanced] [--checks] [--links]
# 例: npm run review -- evidence --checks     → reviews/evidence-<日付>.md(git には入れない)
```

- 載るもの: ① 判定の要約(🔴 公開を止める理由 / 🟡 確認してほしい点 / 高リスクか)② 設計の要点(根拠の種類、なぜ学ぶのか、前提、段階の範囲)③ レッスンごとの確認の状況・出典の表・変更履歴・記録の注記と、そこから抽出した「限界の可能性」・別の目の確認の結果 ④ 外部リンク(`--links`)⑤ 検査の結果(`--checks`: 型、ビルド、全テスト、まっさらな環境でのビルド)。
- 🔴 になるもの: 出典の記録がない、未確認、法令・基準のゲートを通らない、検査の失敗、リンク切れ。
- 🟡 になるもの: 一部だけ確認・独自の整理、確認日が古い、注記に限界を示す語(要旨・未読・第三者・取得できない など)、**別の目の確認が未実施、または、そのあとに本文が変更された**、確認できない外部リンク。
- **別の目の確認の結果**は、`verify-lesson` が `docs/verify/<レッスン ID>.md` に保存する(1行目は `# 別の目の確認: <ID>(YYYY-MM-DD)`)。コミットして残し、確認の材料が取り込む。
- 機械が見つけられるのは、記録と本文の「形」の問題まで。主張が出典に裏づくかは、別の目の確認が担い、その結果を人が読む。**機械が 🟢 でも、中身の正しさを保証するものではない。**
- 人の確認: 高リスクの分野は、全レッスンを読む。それ以外は、材料の 🔴 と 🟡 を見て判断する。

## 既知の落とし穴
- `pkill -f` は、自分のシェルを止めることがある。サーバーは、プロセス ID を指定して止める。
- PubMed・PMC・一部の出版社は、自動アクセスを遮断する(403・reCAPTCHA)。Europe PMC の API、公式の PDF の写し、書誌の API を試す。
- WebFetch の結果が長いと、途中で切れる。`offset` で続きを読む。読んでいない部分の主張はしない。
- WebFetch は、取得した内容を**要約モデルに通す**ので、返ってくる「引用」は、逐語に近い要約であって、原文の逐語とは限らない。本文で「〜と述べている」と書く定義・数字は、`curl` で生の HTML(PDF なら取り出したテキスト)を取得して、文言を逐語で照合する(`st-1` で行った方法)。
- ブラウザのテストには、ブラウザの共有ライブラリが要る(環境によっては、手元に用意する)。ビルドを先にしてから、テストを流す。
- リポジトリ名・フォルダ名を変えるときは、公開 URL(進捗の保存先)が変わることに注意する。
