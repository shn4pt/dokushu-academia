# レビュー依頼のひな形

別のレビュー担当(AI を含む)に、PR のレビューを頼むときの文面。`<…>` を差し替えて、PR のコメントに投稿する。依頼文を PR に残すと、依頼の経緯がたどれ、結果もコメントで受け取れる(コピーの往復が要らない)。

```markdown
## レビュー依頼

この PR(ブランチ <ブランチ名>)は、Issue #<番号>「<題名>」への対応です。レビューをお願いします。

### 目的
<誰の、どんな学びを、どう良くしたいか>

### 範囲
- <今回の対象>。<対象外(別の PR や、評価後に進めるもの)>
- 対象: <ファイル>

### 見てほしい観点
1. **Issue の完了条件と編集上の制約**: <Issue の完了条件・制約>
2. **読みやすさ(PC 幅・スマートフォン幅)**: <対象の画面>。実画面は、ブランチで `npm ci && npm run build && npx vite preview` を実行して確認する(プレビュー URL は無い)。
3. **判断の妥当性**: <記録(docs/…)の判断に、見落としや過剰がないか。数値は再計算する>
4. **本文の正確さ**: 出典の主張が、元の記事と合っているか(元の URL を直接取得して照合する。照合の記録は docs/verify/<ID>.md)。新しく足した部分に、出典の主張と誤読されうる記述がないか。
5. **時間の扱い**: 目安は実測でなく、アプリの式による。説明が正直か。
6. **クイズ**: 正解の位置の偏り、理解・適用を問えているか、位置以外の手がかり(長さ、言い回し)がないか。
7. **テスト**: 追加した検査が、壊れにくく、意味があるか。

### 実行済みのチェック
<コマンドと結果>

### 既知の限界
<未実施のこと、意図して軽くとどめたこと>

### 報告の形式
- **結果は、この PR のコメントに投稿してください。**
- 重大度順(修正が必要、望ましい、任意)に、場所と理由、できるだけ具体的な修正の文面を書いてください。
- 確認した範囲と、していない範囲(元の記事を取得して照合したかも)を分けて書いてください。
- マージはしないでください。
```
