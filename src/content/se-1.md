### 守るものを決めないと、守り方は決まらない

「セキュリティを強化してほしい」という要望は、そのままでは開発チームが動けません。何を守るのか、何が起きると困るのか、誰が何のために攻めてくるのかが決まって、はじめて、どこにどれだけ手間をかけるかが決まります。このレッスンでは、守る対象の考え方、攻撃者の考え方、守り方の古典的な原則を見ます。

### 何を守るのか:機密性・完全性・可用性

米国の連邦政府の情報の分類の基準 **FIPS 199**(NIST、2004 年 2 月)は、情報セキュリティの目的を、米国の法律(44 U.S.C. 3542)の定義を引いて、次の 3 つにまとめます。

| 目的 | 定義(要約) | 失われると |
|---|---|---|
| **機密性**(confidentiality) | 情報へのアクセスと開示についての、認められた制限を守ること。個人のプライバシーや独自の情報を守る手段を含む | 許されない**開示** |
| **完全性**(integrity) | 情報の不適切な変更や破壊を防ぐこと。否認できないことと、本物であることの確保を含む | 許されない**変更や破壊** |
| **可用性**(availability) | 情報に、適時に、確実にアクセスして使えるようにすること | アクセスや利用の**妨げ** |

FIPS 199 の特徴は、3 つの目的ごとに、**失われたときの影響の大きさ**を、低・中・高の 3 段階で見積もる点です。

- **低**:組織の業務、資産、個人に、**限られた**悪影響が出ると見込まれる。
- **中**:**深刻な**悪影響が出ると見込まれる。
- **高**:**重大または壊滅的な**悪影響が出ると見込まれる(人命にかかわる場合を含む)。

文書は、例として、Web サーバーで**公開情報**を扱う組織は、機密性の影響は「該当なし」、完全性と可用性は「中」とする、という見積もりを挙げます。(このサービスの読みでは、公開している情報なので漏れても困らないが、勝手に書き換えられたり、見られなくなったりすると困る、ということです。)文書は、**同じシステムの中でも**、情報の種類ごとに見積もる例も挙げます。調達のシステムが、公告前の契約の情報(機密性・完全性は中、可用性は低)と、日常の事務の情報(すべて低)を扱う場合です。システム全体の区分は、それぞれの目的について、最も高い値をとります。(FIPS 199 は米国の連邦政府の情報システムのための基準です。民間の会社に義務を課すものではありません。考え方が広く参照されている、というのは、このサービスの補足です。)

### 誰から守るのか:攻撃者を理解する

Google の技術者らによる本 *Building Secure and Reliable Systems*(Google が公開しているウェブ版)の第 2 章(Heather Adkins と David Huska、協力 Jen Barnason)は、**攻撃者を理解する**ための枠組みを 3 つ示します。動機、人物像、方法です。章は、攻撃者を「暗い地下室の、あだ名を持つ人」という固定観念で考えず、**時間か知識かお金があれば、誰でもシステムの安全を損なえる**、と述べます。

章が挙げる**動機**は、楽しみ、名声、社会運動、金銭、強要、操作(偽の情報の公開など)、諜報、破壊です。1 人の攻撃者が、いくつもの動機を同時に持つこともある、と書いています。

**人物像**の例として、章は次を挙げます。

| 人物像 | 章の説明の要点 |
|---|---|
| 趣味の人 | 仕組みを知りたいという好奇心で動き、たいていは害を与えないという個人の倫理に従う。組織の味方になりうる |
| 脆弱性の研究者 | 多くはシステムを良くしたいという動機を持ち、報告の作法(見つけた弱点の報告と公開の手順)に沿って動く傾向がある |
| 政府 | 諜報、軍事、国内の取り締まりのために侵入することがある。自分が狙われるとは思っていなかった組織が狙われた例もある |
| 活動家 | 社会の変化を訴えるために、Web サイトの書き換えやサービス妨害をすることがある |
| 犯罪者 | なりすまし、金銭の窃取、恐喝など。技術力はさまざまだが、**最も手間と費用の少ない方法**を選びがち |
| 内部の人 | 社員、委託先、オープンソースの貢献者、家族など。悪意のある行動だけでなく、**うっかりした誤り**も含む |

内部の人について、章は、悪意か過失かは見分けにくいので、**両方を想定して設計する**よう勧めます。そのための考え方として、**最小権限**(仕事に必要な最小限の権限を、必要な期間だけ与える)、複数人の承認、アクセスの理由の記録、監査、壊されても戻せること、などを挙げます。

章は、リスクを見積もるときの注意として、次のようなことを述べます。

- **自分が狙われていると気づかないことがある**。小さな組織でも、ほかへの攻撃の踏み台に使われうる。
- **攻撃の高度さは、成功の予測にならない**。攻撃者は、たいてい、目的を満たす最も簡単で安い方法を選ぶ。影響の大きかった諜報活動の中にも、パスワードをだまし取る、ごく基本的な手口(フィッシング)に頼ったものがある。だから、まず**2 要素認証のような基本**を押さえてから、珍しい攻撃を心配する。
- **攻撃者を軽く見ない**。ただし、極端に資源を使う攻撃は、例外であって普通ではない。
- **誰がやったかの特定は難しい**。誰かより、どう攻めるかに先に注目する。

### どう守るのか:1975 年の 8 つの設計原則

守り方の考え方として、今も引用されるのが、Jerome Saltzer と Michael Schroeder の 1975 年の論文 *The Protection of Information in Computer Systems* です(大学の講義のページにある、ウェブ版の写しを読みました)。論文は、欠陥のないシステムを作る方法は誰も知らないので、欠陥の数と深刻さを減らす助けになる、**経験からの 8 つの設計原則**を挙げます。

| 原則 | 要点 |
|---|---|
| 仕組みの経済性 | 設計はできるだけ単純で小さく。不正な経路は通常の使い方では気づかれないので、1 行ずつ確かめられる小ささが要る |
| 安全側の初期値 | アクセスの判断は、**許す理由**にもとづく。初期状態は「アクセスできない」にする |
| 完全な仲介 | **すべての**対象への、**すべての**アクセスで、権限を確かめる |
| 公開設計 | 仕組みを秘密にすることに頼らない。守るのは、鍵やパスワードのような、守りやすいものにする |
| 権限の分離 | 可能なら、2 つの鍵がそろわないと開かないようにする |
| 最小権限 | すべてのプログラムと利用者は、仕事に必要な最小限の権限で動く |
| 共通の仕組みの最小化 | 複数の利用者が共有し、全員が頼る仕組みを、できるだけ少なくする |
| 心理的な受け入れやすさ | 使いやすく作り、利用者が自然に正しく守りの仕組みを使えるようにする |

「安全側の初期値」について、論文は、許可を与える仕組みの誤りは「拒否」として現れ、すぐに気づかれるが、拒否する仕組みの誤りは「許可」として現れ、通常の使い方では気づかれないかもしれない、と理由を述べます。

ただし、論文は、これらの原則は**絶対の規則ではなく、警告として最もよく働く**、と書いています。設計がある原則に反しているなら、それは問題の兆しなので、その問題が考慮済みか、重要でないかを確かめるべきだ、という使い方です。

(「心理的な受け入れやすさ」は、[UX の講座](/course/ux)で見た、使いやすさの話と同じ方向です。また、[SWE-5](/lesson/sw-5)で見た Parnas の情報隠蔽と、「仕組みの経済性」「共通の仕組みの最小化」は、境界を小さく保つという点で通じます。どちらも、このサービスの対応づけです。)

### PM がセキュリティの相談で使える問い(このサービスの整理)

ここからは、このサービスの整理です。

1. **この機能が扱う情報は何か。3 つの目的のうち、どれが失われると最も困るか。** 公開情報なら完全性と可用性、個人情報なら機密性、決済なら完全性、のように、重みは情報ごとに違う(FIPS 199 の考え方)。
2. **失われたときの影響は、どれくらいか。** 限られた、深刻な、壊滅的な、のどれに近いか。
3. **誰が、何のために狙いうるか。** お金、情報、評判、抗議、うっかり。内部の人や、自分たちが踏み台になる可能性も含める(第 2 章)。
4. **基本は押さえているか。** 珍しい攻撃の前に、2 要素認証、最小権限、初期値を「拒否」にすること、などの基本ができているか。

### この講座の出典と限界

このレッスンの出典は、**米国の標準、実務家の著作、古典的な論文**(FIPS 199、*Building Secure and Reliable Systems* の第 2 章、Saltzer と Schroeder 1975)で、この講座の根拠の基準(論文、公式の文書、標準)に沿っています。

- FIPS 199 は、米国の連邦政府の情報システムのための基準です。日本の法令や、民間の会社の義務を示すものではありません。
- 第 2 章の攻撃者の分類は、章自身が「説明のための一般化で、決定的なものではない」と断っています。章が挙げる個別の事件の例は、このレッスンでは使っていません。
- Saltzer と Schroeder の論文は 1975 年のもので、論文の第 II 節以降(保護の仕組みの詳細)は読んでいません。読んだのは、第 I 節の設計原則の部分と要旨です。
- このレッスンは、考え方の入門です。実際のシステムの安全性の判断は、専門家による評価が必要です。
