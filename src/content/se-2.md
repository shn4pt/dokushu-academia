### 「誰か」を確かめることと、「何をしてよいか」を決めること

ログインの仕組みや権限の設計は、多くのプロダクトで、PM が仕様を決める場面のある話題です。このレッスンでは、よく混同される 2 つの言葉、**認証**と**認可**を分け、それぞれについて、標準と実務家の指針が何を求めているかを見ます。

OWASP(Web アプリのセキュリティの指針をまとめる団体)の *Authorization Cheat Sheet* は、NIST の定義を引いて、**認可**を「要求された操作やサービスが、特定の主体に認められているかを確かめる過程」と説明し、**認証**(主体が誰かを確かめる過程)とは別のものだ、と述べます。

| | 認証(authentication) | 認可(authorization) |
|---|---|---|
| 問い | あなたは誰か | あなたは、これをしてよいか |
| 例 | パスワード、2 要素認証でログインする | 一般の利用者は自分の注文だけ見られ、管理者は全員の注文を見られる |

文書は、ログインした(認証された)利用者が、システムで技術的にできることのすべてを許されているとは限らない、と注意します。逆に、ログインしていない利用者でも、公開のページのように、見てよいものもあります。

### 認証:NIST SP 800-63B-4 のパスワードの規則

米国の NIST が 2025 年 7 月に出したデジタル ID の指針 **SP 800-63B-4**(*Authentication and Authenticator Management*)は、認証を、利用者が、本人のものとして登録された**認証器**(パスワード、ワンタイムのコードを出す道具、鍵など)を管理していることを確かめる過程として扱います。指針は、パスワードを「知っているもの」、物理的な認証器を「持っているもの」、生体の照合を「本人の特徴」と呼び分けます。

パスワードについて、指針は、多くの人の直感に反する規則を定めています(「SHALL」は必須、「SHOULD」は推奨の意味です)。

| 規則 | 指針の書き方 |
|---|---|
| 長さ | パスワード**だけ**で認証するなら、**15 文字以上**を求めなければならない(多要素の一部なら 8 文字以上でよい)。最大で 64 文字以上は受け付けるべき |
| 文字の組み合わせ | **英大文字・数字・記号を混ぜる、といった組み合わせの規則を課してはならない** |
| 定期的な変更 | **定期的な変更を求めてはならない**。ただし、漏れた証拠があれば、変更させなければならない |
| 禁止リスト | よく使われる、予想される、漏えいしたパスワードの一覧と照らし、当たったら別のものを選ばせ、理由を示さなければならない |
| ヒントと秘密の質問 | 認証の前の人が見られるヒントの保存を許してはならない。パスワードを選ぶときに、「最初のペットの名前は?」のような秘密の質問を使わせてはならない |
| パスワード管理ソフト | 自動入力を許さなければならない。貼り付けも許すべき |
| 試行の回数 | 失敗した試行の回数を、実効的に制限しなければならない |
| 保存 | ソルト(ランダムな値)を加えて、パスワード専用のハッシュの方式で保存しなければならない |

組み合わせの規則を課さないことについて、指針は、理由を付録(*Strength of Passwords*)に書いている、と述べています。(付録そのものは、このレッスンでは読んでいません。)パスワード管理ソフトについては、それを使うと、利用者がより強いパスワードを選びやすくなることが示されている、と述べています。

### フィッシングに強い認証

指針は、**フィッシング耐性**を、利用者の注意深さに頼らずに、偽のサイトに認証の秘密や有効な出力を渡さないようにできる、認証のやり方の性質と定義します。そして、**SMS で届くコードや、画面に表示されるワンタイムのコードを手で入力する方式は、フィッシングに強いとはみなさない**、と書きます。手で入力したコードは、特定のセッションに結びつかないので、偽のサイトがそのコードを本物のサイトに中継してログインできてしまうからです。フィッシングに強い方式には、暗号を使った認証が必要だ、とします。

指針は、2 要素以上が必要な水準(AAL2)では、**フィッシングに強い認証の選択肢を少なくとも 1 つ提供しなければならない**(SHALL)と定めています。連邦機関は、職員や委託先などに、フィッシングに強い認証を使わせなければならない、とも定めます。また、電話網(SMS や音声)でコードを送る方式を、現時点で唯一の「制限付き」の認証器としています。使う組織は、そのリスクを評価して受け入れる必要があり、利用者には、制限のないほかの認証器を少なくとも 1 つ用意し、リスクを知らせなければならない、としています。

([前のレッスン](/lesson/se-1)で見た Google の本の第 2 章は、影響の大きかった諜報活動の中にもフィッシングに頼ったものがあり、まず 2 要素認証のような基本を押さえるべきだ、と述べていました。)

### 認可:OWASP の推奨

OWASP の *Authorization Cheat Sheet* は、認可の欠陥は Web アプリの目立つ懸念で、**アクセス制御の不備**(Broken Access Control)が、OWASP の 2021 年の Top 10 で、最も懸念される Web の脆弱性とされた、と述べます。文書は、ログインした利用者が**ほかの利用者の資源にアクセスできてしまう**こと(水平の権限昇格)が、特によくある弱点だ、と書きます。

文書の推奨のうち、このレッスンで読んだ前半の 5 つと、確認の場所についての推奨は、次のとおりです。

1. **最小権限を徹底する**:利用者の種類、扱う資源、操作(読む、書くなど)を設計の段階で洗い出し、組み合わせごとに許す操作を決める。決めた権限が守られているかを確かめるテストを作る。公開後も、権限が少しずつ膨らんでいないか(privilege creep)を定期的に見直す。**あとで権限を取り上げるより、あとで足すほうが易しい**。
2. **初期値は拒否**:どのルールにも当たらないときは、アクセスを拒否するように設定する。権限を与えた理由を説明できるようにする。
3. **すべての要求で権限を確かめる**:確認が 1 か所でも漏れれば、資源が危うくなる。大半の要求で確かめるだけでは足りない。
4. **道具の認可の仕組みを鵜呑みにしない**:フレームワークの初期設定に頼らず、必要なら独自の確認を加える。
5. **役割(ロール)だけで決めるより、属性や関係で決める方式を一般に優先する**:役割による方式(RBAC)は、対象ごとや、ほかの利用者との間の(水平の)判断が苦手だ、と述べます。関係による方式(ReBAC)の例として、「投稿を作った本人だけが編集できる」を挙げています。
6. **確認は正しい場所で行う**:画面側(クライアント側)の確認に頼ってはならない。使いやすさのために画面側で確かめるのはよいが、許可の決め手にしてはならず、確認はサーバー側などで行う、と述べます。

(2 と 3 は、[前のレッスン](/lesson/se-1)で見た Saltzer と Schroeder の「安全側の初期値」と「完全な仲介」と同じ考え方です。これは、このサービスの対応づけです。)

### PM がログインと権限の仕様で使える問い(このサービスの整理)

ここからは、このサービスの整理です。

1. **パスワードの規則を、昔の慣習で決めていないか。** 「記号を必ず入れる」「90 日ごとに変更」は、SP 800-63B-4 が「してはならない」としている。代わりに、長さ、漏えいしたパスワードの禁止、試行の制限、パスワード管理ソフトへの対応を確かめる。(米国の連邦政府向けの指針なので、自社が従う義務があるかは別の問題です。)
2. **2 要素目は、何にするか。** SMS のコードは、フィッシングに強いとはみなされない。扱う情報の重さに応じて、フィッシングに強い方式を選べるようにするか。
3. **画面に表示しないだけで、守ったことにしていないか。** 権限の確認は、サーバー側で、すべての要求について行われているか(OWASP の推奨 3 と 6)。
4. **権限の一覧はあるか。** 利用者の種類 × 資源 × 操作の表を作り、それをテストにできるか。権限の見直しの時期を決めているか。

### この講座の出典と限界

このレッスンの出典は、**標準と、実務の指針**(NIST SP 800-63B-4 の本文、OWASP の Authorization Cheat Sheet)です。

- SP 800-63B-4 は、米国の連邦政府の情報システムに向けた指針です。日本の法令や、民間の会社の義務を示すものではありません。2025 年 7 月の版で、2017 年の版(2020 年に更新)を置き換えたものです。このレッスンで読んだのは、序論、AAL の節(第 2 章)、パスワードの節、電話網による方式の節、フィッシング耐性の節、制限付きの認証器の節で、付録などは読んでいません。
- OWASP の文書は、実務家の共同の指針です。推奨のうち、ID の推測や改ざんへの対策、失敗時の安全な終了、ログ、テストなどの節は、このレッスンでは扱っていません。文書は、根拠の多くを他の資料(OWASP Top 10、MITRE の CWE、Veracode の報告書)に置いています。それらの元の資料は、このレッスンでは読んでいません。
- このレッスンは、考え方の入門です。実際の認証や権限の設計の安全性は、専門家による評価が必要です。
