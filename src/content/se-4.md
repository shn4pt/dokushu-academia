### 秘密は、コードの中に置かない

プロダクトは、たいてい外部のサービスとつながっています。決済、地図、メール、クラウドの保存領域、そして AI の API。つなぐたびに、**API キー**、データベースのパスワード、暗号の鍵といった**秘密情報**(シークレット)が増えます。このレッスンでは、秘密が実際にどれくらい漏れているか、どう管理し、漏れたらどうするかを見ます。

### 公開のリポジトリで、秘密はどれくらい漏れているか

ノースカロライナ州立大学の Meli、McNiece、Reaves による論文 *How Bad Can It Git? Characterizing Secret Leakage in Public GitHub Repositories*(NDSS 2019)は、GitHub の公開のリポジトリで、秘密がどれくらい漏れているかを大規模に調べました。論文は、自分たちの研究を、この問題についての最初の大規模で、時間を追った分析だ、と位置づけています。

方法は 2 つです。約 6 か月(2017 年 10 月〜2018 年 4 月)、新しく公開されたコミットをほぼ実時間で調べる方法と、公開のリポジトリの 13% を含むスナップショットを調べる方法です。対象は、秘密鍵のファイルと、形式がはっきりした 11 のサービスの API キーに絞りました。主な結果は次のとおりです。

- 漏えいは広く起きていて、**10 万を超えるリポジトリ**に及び、**毎日、何千もの新しい秘密**が漏れている。実時間の方法では、1 日あたりの中央値で 1,793 の固有の秘密の候補を集めた。
- 既知の文字列を公開のリポジトリに push し、それが GitHub の検索で見つかるまでの時間を測った実験では、中央値は **20 秒**だった。論文は、自分たちの方法がほぼ実時間で秘密を見つけられ、誤って公開したことに気づいても、直す時間はほとんどない、と述べる。
- 見つけた秘密のうち、約 2 週間のあいだに消されたのは **19%** で、その多くは最初の 24 時間のうちだった。**81% は消されなかった**。
- 消された場合も、多くはリポジトリを消すのではなく、秘密を消すコミットを追加していた。Git の仕組みでは、秘密は**履歴に残り、まだ取り出せる可能性が高い**。
- 主な原因は、暗号の鍵のファイルを入れてしまうことと、**API キーをコードに直接書く**ことだった。
- 当時の対策(コミット前の検出の道具、複数の値を組み合わせる鍵、検索の回数の制限)は、どれも大規模な漏えいを抑えられていなかった。たとえば、ある検出の道具は、この研究の秘密の約 25% しか見つけられなかった。

論文は、自分たちの方法は保守的で、結果は**下限**であり、実際はもっと悪いだろう、と書いています。一方で、限界として、見つけた秘密が本当に悪用できるかは(倫理上の理由で)試しておらず、無効や失効済みのものが含まれうること、調べたのは一部のサービスと GitHub だけであること、を挙げています。

### 管理の考え方:OWASP のガイド

OWASP の *Secrets Management Cheat Sheet* は、多くの組織が、秘密をソースコードに平文で書き込み、設定ファイルにまき散らしている、と書き出します。そして、秘密の保管、発行、監査、交換、管理を**一元化**する必要が高まっている、と述べます。複数のサービスが同じ秘密を共有していると、どこから漏れたのか分かりにくい、とも指摘します。

文書の主な推奨は、次のとおりです。

| 考え方 | 文書の説明の要点 |
|---|---|
| 一元化と標準化 | 秘密の管理の仕組みを、方針をそろえて一元化する。秘密が何に使われ、どこにあるかが、すぐ分かるようにする |
| アクセス制御 | 秘密を読める人は、その人と端末を通じて漏らしうる。全員にすべての秘密を見せず、最小権限にする |
| 自動化 | 手作業は、漏えいと人の誤りの危険を増やす。秘密への人の関与を減らす。可能なら、使うたびに作る**動的な秘密**を使い、短い期限をつける |
| 監査 | 誰が、どのシステムのために秘密を求め、いつ使い、いつ期限が切れたかなどを、改ざんされない形で記録する |
| ライフサイクル | 作成、交換(ローテーション)、失効、期限切れ、の段階で管理する。秘密は、できるだけ期限が切れるように作る |
| 記録に残さない | 秘密は**決してログに残さない**(暗号化か伏せ字にする) |

交換(ローテーション)について、文書は、盗まれた秘密が短い時間しか使えないように、**定期的に交換すべき**だ、と述べます。ただし、**利用者の資格情報(パスワードなど)は定期的な交換の対象外**で、漏れた疑いや証拠があるときだけ交換する、と NIST の推奨を引いています([セキュリティ-2](/lesson/se-2)で見た規則と同じです)。つまり、システムどうしの秘密(API キーなど)と、人の資格情報とでは、交換の考え方が違います。

### 秘密は、どこに置くか

**The Twelve-Factor App**(Web アプリの作り方の原則をまとめた実務家の文書)の「設定」の章は、設定(データベースの接続先や、外部サービスの資格情報など、配備の環境ごとに変わる値)を、**コードから厳密に分けて、環境変数に置く**ことを勧めます。コードに設定がきちんと分けられているかの試金石として、**資格情報を漏らさずに、いつでもコードを公開できるか**、を挙げています。設定ファイルをリポジトリに入れない方法は、定数をコードに書くよりはるかに良いが、誤って入れてしまいやすい、とも述べます。

一方で、OWASP の文書は、コンテナの中のアプリに秘密を渡す方法として、ファイルとして差し込む、秘密の管理の仕組みから実行時に取りに行く、**環境変数**の 3 つを挙げ、環境変数については、ふつう全プロセスから読め、**ログやダンプに含まれうるので、ほかの方法が使えない場合を除いて勧めない**、と書いています。秘密をコンテナのイメージに焼き込むことも、勧めていません。

(2 つの文書は、「コードに秘密を書かない」点では一致し、置き場所としての環境変数の評価が違います。Twelve-Factor App の文書は、コードとの分離を主に論じたもので、OWASP の文書は、コンテナでの漏えいの経路を論じています。どちらを選ぶかは、仕組みと脅威に応じて専門家と決めるべきことです。この比較は、このサービスの整理です。)

### 漏れたら、まず失効させる

OWASP の文書は、秘密が漏れたときの**事故対応**について、すばやい対応は秘密の管理で最も重要な点の一つで、事故対応の第一の目標はすばやい対応と封じ込めだ、と述べ、次の手順を挙げます。

1. **失効**:漏れた鍵は、ただちに失効させる。すばやく無効にでき、失効の状態が分かる仕組みを用意しておく。
2. **交換**:新しい秘密をすばやく作り、置き換える。できれば自動で。
3. **削除**:漏れた場所(コードやログ)から消す。コードの履歴を書き換えて消すこともできるが、ほかへのリンクを壊すなどの問題があるので、影響を理解して計画する。
4. **記録**:誰が秘密にアクセスでき、いつ使い、前回いつ交換したかを、対応する人が見られるようにする。

(Meli ほかの論文の結果と合わせると、履歴から消すだけでは不十分で、**失効と交換が先**だ、ということになります。公開から検索で見つかるまでが数十秒という実験の結果もありました。これは、このサービスのまとめです。)

### PM が秘密の扱いで使える問い(このサービスの整理)

ここからは、このサービスの整理です。

1. **この機能で、新しい秘密はいくつ増えるか。誰が持ち、どこに置くか。** コードや共有のドキュメントに、平文で書かれていないか。
2. **漏れたら、何分で止められるか。** 失効と交換の手順と担当は決まっているか。交換すると、何が止まるか(依存の一覧)。
3. **秘密を見られる人は、必要な人だけか。** 退職や異動のときに、外しているか。
4. **ログや画面に、秘密が出ていないか。** エラーの表示、ログ、問い合わせの記録など。
5. **人のパスワードと、システムの秘密を、同じ規則で扱っていないか。** システムの秘密は定期的に交換し、人のパスワードは漏れたときに変えさせる。

### この講座の出典と限界

このレッスンの出典は、**査読つきの論文、実務家の共同の文書、実務家の原則**(Meli ほか 2019、OWASP の Secrets Management Cheat Sheet、The Twelve-Factor App の「設定」の章)です。

- Meli ほかの論文は 2017〜2018 年のデータで、GitHub の公開のリポジトリと、一部のサービスの秘密に限った研究です。論文の時点の対策の評価(検出の道具の性能など)は、その後の道具の改善を反映していません。論文が触れている GitHub の新しい機能(当時はベータ版)のその後は、このレッスンでは確かめていません。
- OWASP の文書は、読んだのは、序論、一般的な管理(一元化、アクセス制御、自動化、監査、ライフサイクル)、CI/CD での置き場所、コンテナへの渡し方、検出、事故対応の節です。クラウドごとの節や暗号の節は読んでいません。
- 具体的な仕組み(どの秘密の管理の仕組みを使うかなど)は、使っている環境と脅威によって違うので、専門家の確認が必要です。
